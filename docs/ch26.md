# 第26章 L2CAP：振り分けと分割

::: goal
- L2CAP の3つの仕事を説明できる
- クレジット方式のフロー制御の動きを追える
- ATT の MTU とリンク層のデータ長から、パケットの数を計算できる
- 「20バイトの壁」が生まれる理由を説明できる
:::

ここから第IV部です。第III部ではコントローラの話をしてきました。ここからは、電波の上にデータの世界を作るホストの層を、下から順に見ていきます。

**L2CAP**（Logical Link Control and Adaptation Protocol）は、ホストの一番下にある層です。名前は長いのですが、仕事は3つだけです。

1. データを正しい宛先の層へ**振り分ける**
2. 受信側があふれないように**流量を調整する**
3. 大きなデータを**分割し、組み立て直す**

## 26.1 振り分け：チャネル

L2CAP の上には、ATT や SMP のような複数のプロトコルが載っています。リンク層から届いたデータを、誰に渡せばいいのでしょう。

L2CAP はデータの流れを**チャネル**で区別します。すべての L2CAP パケットの先頭には、宛先を示す **チャネル ID（CID）** が入っています。

Classic では、必要なときに動的チャネルを開いて使うのが普通でした（[第13章](./ch13)）。LE では、これから見る ATT の固定チャネルが中心です。

チャネルには2種類あります。

- **固定チャネル**：準備なしですぐ使える。ATT は `0x0004`、SMP は `0x0006` と決まっている
- **動的チャネル**：必要なときに作る。作るときに **PSM** という番号で相手のサービスを指定する

::: bio
タンパク質の行き先を決めるシグナル配列に似ています。リボソームから出てきたタンパク質は、先頭の短い配列を目印に、小胞体やミトコンドリアへ仕分けられます。CID は中身そのものとは関係のない「行き先の札」です。
:::

::: se
TCP/UDP のポート番号に近いものです。`0x0004` が ATT に予約されているのは well-known ポートに、PSM はポートを指定してソケットを開くのに似ています。
:::

## 26.2 流量調整：クレジット方式

データを送る速さが、受信側の処理より速いと、受信バッファがあふれてデータが失われます。これを防ぐしくみが**フロー制御**です。L2CAP が使うのは**クレジット方式**です。

送信側は「あと何個送ってよいか」という残高（クレジット）を持っていて、次のように動きます。

::: analogy
回転寿司で、自分のテーブルに置ける皿の枚数が決まっていて、食べ終えた分だけ次を流してもらう、というようなものです。お店の人は客が処理できる量を超えて流しません。
:::

ここでひとつ、知っておくと役立つ注意があります。

従来の ATT（第27章）を運ぶ固定チャネルは**基本モード**で動作し、フロー制御を**行いません**。第22章で学んだリンク層の再送は「相手のスタックまで」届くことを保証しますが、そこでバッファがあふれれば、データは捨てられてしまいます。つまり、相手のアプリにデータが届く保証はないのです。

新しい **EATT**（第27章）はクレジット方式のモードを使うので、この問題がありません。

## 26.3 分割と組み立て

層ごとに、一度に扱えるサイズの上限（MTU）が違います。合わないときには分割が必要です。L2CAP の上と下で、それぞれ呼び名が違います。

| どことの関係か | 分ける | 組み立てる |
|---|---|---|
| 上の層のデータ（SDU）を L2CAP の PDU にする | セグメンテーション | リアセンブリ |
| L2CAP の PDU をリンク層のパケットに載せる | フラグメンテーション | リコンビネーション |

具体的に計算してみましょう。アプリが 100 バイトの通知を送りたいとします。ATT の MTU は 247 バイト、リンク層のパケットのデータ部分は 27 バイトとします。

## 26.4 「20バイトの壁」

LE のアプリを作ると、必ず「一度に20バイトまでしか送れない」という話を聞きます。この数字の由来も計算で分かります。

初期の LE では、リンク層のデータ部分は 27 バイトでした。

<div class="formula">27 バイト − L2CAP のヘッダ 4 バイト − ATT のヘッダ 3 バイト ＝ 20 バイト</div>

ATT の MTU の初期値が 23 バイトなのも、27 − 4 = 23 だからです。分割なしで1パケットに収まる大きさが、このように決められていました。

実は、これはもう壁ではありません。ATT の MTU は接続後に交渉して大きくできます（よく使われる上限は 517 バイトです）。Core 4.2 以降は、リンク層のデータ部分も最大 251 バイトまで広げられます。大きな値にしておけば、分割なしで一気に送れて効率が上がります。さきほどの 100 バイトの例も、データ部分が 251 バイトなら1パケットで送れます。

::: extra MTU 交渉が必要な理由
ATT の MTU は「相手のバッファにどれだけ受けられるか」の問題で、リンク層のデータ長は「1パケットの空中の長さ」の問題です。それぞれ別の層で交渉するので、一方だけ大きくなっていることもあります。多くの場合、スマホの OS が接続後に自動で交渉しますが、結果はプラットフォームによって異なります。
:::

## まとめ

- L2CAP の仕事は、振り分け、流量調整、分割と組み立ての3つである
- CID は行き先の札で、ATT は `0x0004`、SMP は `0x0006`
- クレジット方式では、受信側の余裕の分だけ送信できる
- 従来の ATT は基本モードで動くのでフロー制御がない
- 20 バイトの壁は「27 − 4 − 3」から生まれたが、今は交渉で広げられる

## 確認問題

1. ATT の MTU が 185 バイトのとき、1回の通知で送れるアプリのデータは最大何バイトでしょうか。
2. リンク層のデータ部分が 27 バイトのとき、アプリの 60 バイトのデータ（通知）はリンク層で何パケットになるでしょうか。
3. 受信側のクレジットが 0 のとき、送信側はどうしますか。

::: details 答え
1. ATT のヘッダ 3 バイトを引いて 182 バイトです。
2. ATT で 63 バイト、L2CAP で 67 バイトになります。67 ÷ 27 = 2.48… なので 3 パケットです（ATT の MTU が十分に大きいとします）。
3. 新しいクレジットが届くまで送信を止めて待ちます。
:::
