# 第33章 Classic と LE、どちらを選ぶか

::: goal
- Classic と LE の違いを、しくみの理由とともに説明できる
- 1台の機器が2つの方式を同時に使うときに何が起きているかを説明できる
- 用途に応じて、どちらの方式を選ぶべきかを考えられる
:::

最後の章です。ここまで、第II部で Classic を、第III部と第IV部で LE を見てきました。第1章のランナーのスマホは、Classic でヘッドホンに音楽を流しながら、LE で心拍計から心拍数を受け取っています。2つの Bluetooth を並べて、全体を振り返りましょう。

## 33.1 2つの方式を並べる

ここまで読んできたあなたなら、次の表のどの行も理由つきで説明できるはずです。

| 観点 | Classic（BR/EDR） | LE |
|---|---|---|
| 発想 | 電線を1本張って流し続ける（第1章） | できるだけ眠り、短時間だけ話す（第18章） |
| チャネル | 79本、各 1 MHz（第7章） | 40本、各 2 MHz（第19章） |
| 時間の単位 | 625 µs のスロットが常に刻まれる（第6章） | 接続イベントがときどき訪れる（第22章） |
| 接続中の聞き方 | 既定では、呼ばれるかもしれないスロットを毎回聞く | 約束した時刻だけ聞く |
| 発見 | **探す側**が叫び、探される側は聞く（第8章） | **探される側**が叫び、探す側は聞く（第21章） |
| 再送 | ARQN と SEQN（第10章） | SN と NESN（第22章） |
| 音声 | 予約席の SCO と eSCO（第11章） | アイソクロナス通信の CIS と BIS（第24章） |
| 放送 | CPB（第11章） | アドバタイズ、定期アドバタイズ、BIS（第21、23、24章） |
| 鍵の手続きの担当 | コントローラ（LM）（第15章） | ホスト（SMP）（第30章） |
| サービスの検索 | SDP（第13章） | ATT と GATT（第27、28章） |
| アプリのデータ | プロファイルごとに別のプロトコル（第14章） | GATT の表という共通の形（第28章） |

再送のしくみのように、よく似た考え方を別々に作っているところもあれば、発見の役割のように正反対のところもあります。違いのほとんどは、「流し続ける」か「眠る」かという出発点の違いから説明できます。

速さの違いも見ておきましょう。Classic の電波の速さは BR で 1 Mb/s、EDR で 2 Mb/s と 3 Mb/s です。LE も 1 Mb/s と 2 Mb/s があり、Core 7.0 では最大 7.5 Mb/s の HDT も加わりました（第19章）。「Classic は速く、LE は遅い」とは、もう言い切れません。

## 33.2 同時に使う

ランナーのスマホに戻りましょう。ヘッドホンへの音楽と、心拍計からの心拍数は、同じ 2.4 GHz の電波を使います。両方を載せたコントローラは、2つの方式の予定を調整して、電波の時間を分け合います。第12章で見た資源マネージャが、Classic のスロットと LE の接続イベントの両方をダイヤに組み込むイメージです。

ここで、それぞれの方式の性格が生きてきます。

- Classic の音楽は、5スロットのパケットを送ったあと、次のパケットまで時間に余裕があります（第17章）
- LE の心拍計は、1秒に1回、ほんの数百マイクロ秒だけ話せば済みます（第3章、第22章）

隙間の時間で LE の短いやり取りを済ませられるので、2つの通信は無理なく同居できます。

ヘッドホンの側でも、両方の方式を使う製品が増えています。音楽と通話は Classic の A2DP と HFP で、イヤホンの設定アプリとの通信は LE の GATT で、という具合です。ペアリングも、CTKD を使えば1回で済ませられます（第15章）。

## 33.3 どちらを選ぶか

自分で機器やアプリを作るときの目安をまとめます。

| 目的 | 向いているもの | 理由 |
|---|---|---|
| 高音質の音楽を、今ある機器へ | Classic（A2DP） | 対応機器が圧倒的に多い |
| ハンズフリー通話を、車やカーナビへ | Classic（HFP） | 同上 |
| 複数人への音声の放送、補聴器 | LE Audio（第24章） | BIS は台数無制限の放送ができ、消費電力も低い |
| 小さなセンサのデータ | LE | 電池が何桁も持つ |
| タグ、ビーコン | LE | アドバタイズだけで成り立つ |
| PC とボードの手軽な通信 | Classic（SPP）か LE（GATT） | スマホ（特に iOS）から使うなら LE が無難 |
| ファイルの大量転送 | 状況による | LE の高速 PHY の普及状況を確認する |

この表は本書の目安で、仕様が決めているものではありません。実際に選ぶときは、第31章で見たように、相手の機器と OS が何に対応しているかを必ず確かめてください。

音声の世界では、LE Audio が少しずつ広がっています。LE Audio の LC3 コーデックは、Classic のハンズフリー（HFP v1.9）でも使えるようになりました（第14章）。2つの方式は、競い合いながら、ときに部品を共有しながら進化しています。

## 33.4 おわりに

Classic は「いかに流し続けるか」の技術で、LE は「いかに眠るか」の技術です。2つの Bluetooth は、同じ 2.4 GHz の空間で、まったく違う問いに答えています。そして多くの機器の中で、その2つが隣り合って働いています。

次は実物を観察してみてください。HCI のログを取れば、本書で追いかけた流れがそのまま文字として並んでいるのが見えるはずです（第31章）。もし Core 仕様やプロファイルの仕様書を開いてみて、以前より読めるようになっていると感じたら、この本の役目は果たせたことになります。

## まとめ

- Classic と LE の違いのほとんどは、「流し続ける」か「眠る」かという出発点の違いから説明できる
- 両方を載せた機器は、2つの方式の予定を調整して電波の時間を分け合う
- 音楽と通話は Classic、小さなデータや放送は LE が中心だが、LE Audio のように境目は動いている

## 最後の確認問題

1. 新しい機器を探すとき、Classic と LE では「叫ぶ側」が逆です。それぞれどちらの機器が叫ぶのでしょうか。また、LE がそうできる理由は何でしょうか。
2. スマホがヘッドホンと心拍計に同時につながっているとき、2つの通信はどうやって電波を分け合っているでしょうか。
3. 友達に「ヘッドホンは LE じゃなくて Classic なの？」と聞かれたら、どう答えますか。30秒で説明してください。

::: details 答え
1. Classic では探す側が Inquiry で叫びます。LE では探される側がアドバタイズで叫びます。LE はアドバタイズのチャネルを3本に絞ったので、探す側は聞いているだけで見つけられます。
2. 両方を載せたコントローラが、Classic のスロットと LE の接続イベントの予定を調整し、時間を分けて使っています。音楽のパケットの合間に、心拍計との短いやり取りを入れられます。
3. たとえば：「音楽や電話は、ずっと流し続ける使い方だから、それに合わせて作られた Classic が今も使われているんだ。世の中の機器のほとんどが対応しているから、どの機器ともつながる安心感もある。LE は『短いデータをたまに』が得意で、新しい LE Audio で音声にも進出してきているけど、Classic がいきなり消えることはないと思う。」
:::
