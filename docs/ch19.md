## 19.1 名前について

正式な名前は **BR/EDR** です。BR は Basic Rate、EDR は Enhanced Data Rate の略です。「Classic」は広く使われる通称で、Core 仕様の Architecture 編には一度も出てきません。本書では読みやすさを優先して Classic と書き、仕様の話をするときは BR/EDR と書きます。

Bluetooth はそもそも、機器をつなぐ**ケーブルを置き換える**ために作られました。この出発点が Classic の性格を決めています。つまり、2台の機器のあいだに**見えない電線を1本張り、接続している間はそこにデータが流れ続ける**という発想です。

::: analogy 電話と手紙
Classic は電話に似ています。一度つなぐと回線を握ったままで、いつでも話せます。ただし、つないでいる間はお互いに受話器を耳に当てていなければなりません。

LE は手紙に似ています。普段は何もせず、用があるときだけ短い便りを出します。

どちらが優れているという話ではありません。長い話を途切れずにするなら電話、たまに短い用件を伝えるなら手紙が向いています。
:::

Classic の歩みを Core 仕様の変更履歴でたどると、次のようになります。

| 版 | Classic に関する主な変更 |
|---|---|
| 1.2 | 適応ホッピング（AFH）、eSCO の追加 |
| 2.0 + EDR | EDR（2 Mb/s、3 Mb/s）の追加 |
| 2.1 + EDR | Secure Simple Pairing、EIR、Sniff サブレーティングの追加 |
| 3.0 + HS | L2CAP の Enhanced Retransmission モードと Streaming モード、拡張された電力制御の追加 |
| 4.0 | LE が登場（別の方式として並ぶ） |
| 4.1 | Secure Connections、CPB、Train Nudging、Interlaced Scan の一般化、時計の調整の追加 |
| 5.0 | Slot Availability Mask の追加、Park の削除 |

Core 5 以降の新機能の多くは LE 向けです。Classic は成熟した技術として、大きくは変わらず使われ続けています。

## 19.4 LE との違い

LE を読んだ人のために、違いを表にまとめます。第V部を読み終えるころには、どの行も理由つきで説明できるようになるはずです。

| 観点 | Classic（BR/EDR） | LE |
|---|---|---|
| 発想 | 電線を1本張って流し続ける | できるだけ眠り、短時間だけ話す |
| チャネル | 79本、各 1 MHz | 40本、各 2 MHz |
| 時間の単位 | 625 µs のスロットが常に刻まれる | 接続イベントがときどき訪れる |
| 接続中の聞き方 | 既定では、呼ばれるかもしれないスロットを毎回聞く | 約束した時刻だけ聞く |
| 発見 | **探す側**が叫び、探される側は聞く | **探される側**が叫び、探す側は聞く |
| 音声 | 専用の予約席（SCO, eSCO） | アイソクロナス通信（CIS, BIS） |
| 鍵の手続きの担当 | コントローラ（LM） | ホスト（SMP） |
| サービスの検索 | SDP | ATT と GATT |
| アプリのデータ | プロファイルごとに別のプロトコル | GATT の表という共通の形 |

「鍵の手続きの担当」の違いには、はっきりした理由があります。LE では、チップを安くするために、手間のかかる仕事をホスト側へ移しました。Classic が作られたときには、そういう制約を優先していなかったわけです。

速さの違いも見ておきましょう。Classic の電波の速さは BR で 1 Mb/s、EDR で 2 Mb/s と 3 Mb/s です。LE も 1 Mb/s と 2 Mb/s があり、Core 7.0 では最大 7.5 Mb/s の HDT という PHY も加わりました。「Classic は速く、LE は遅い」とは、もう言い切れません。それでも音声やデータを流し続ける製品に Classic が使われているのは、**長年の互換性**があり、機器の組み合わせを選ばずにつながるからです。

### 元にした資料

第V部は、Bluetooth Core Specification v7.0 の [Architecture 編](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core_v7.0/out/en/architecture%2C-change-history%2C-and-conventions/architecture--arch-.html)（Vol 1 Part A）を骨組みにしています。ただし Architecture 編は設計の考え方を説明する文書で、具体的な数字はあまり載っていません。625 µs のスロットやパケットの種類などは、同じ Core 仕様の別の編で確認して補いました。

本書では仕様書の場所を次のように書きます。

| 略号 | 仕様書の場所 | 内容 |
|---|---|---|
| ARCH | Vol 1 Part A | アーキテクチャ（骨組みにした編） |
| RF | Vol 2 Part A | 無線 |
| BB | Vol 2 Part B | ベースバンド |
| LMP | Vol 2 Part C | リンクマネージャのプロトコル |
| SEC | Vol 2 Part H | セキュリティ |
| L2CAP | Vol 3 Part A | L2CAP |
| SDP | Vol 3 Part B | サービス検索 |
| GAP | Vol 3 Part C | 発見と接続の作法 |
| HCI | Vol 4 Part E | HCI |

たとえば「BB §8.4」は、ベースバンド編の 8.4 節です。

LE 編と同じく、これは**翻訳ではありません**。話の順番は本書の読者に合わせて組み替え、文章と図は書き下ろしました。Core 仕様の外にある内容（プロファイルの詳細や過去の攻撃の話など）は、「コア仕様の外からの補足」という枠で区別します。全体の対応は[付録D](./core-map)にまとめました。

::: extra コア仕様の外からの補足：古い呼び名
古い資料では、Central と Peripheral は **Master** と **Slave** と書かれています。第23章で出てくる APB と CPB も、以前は ASB、CSB（S は Slave）と呼ばれていました。ネット上の解説やソースコードの多くは今も古い名前を使っています。
:::

::: spec
- **ARCH §1.2、§1.4**：LE の概要と、仕様で使う用語の一覧
- **ARCH §2**：適合試験のしくみ（Upper Tester と Lower Tester）。機器が仕様どおりに動くかを、試験装置で上下から挟んで確かめる
- **ARCH §6.4〜6.5、§8、§9**：GATT、方向探知、Channel Sounding。本書では LE 編で扱った
:::

## まとめ

- 正式名は BR/EDR で、Classic は通称である
- 「ケーブルの置き換え」として生まれ、つないでいる間はデータが流れ続ける発想で作られている
- スタックはホストとコントローラに分かれる。ペアリングの担当がコントローラにある点などが LE と違う
- プロファイルの多くは Core 仕様の外にある
- 第V部は Core v7.0 の Architecture 編を骨組みに、翻訳ではなく書き下ろしている

## 確認問題

1. BR/EDR のみの機器と LE のみの機器は通信できるでしょうか。スマートフォンがどちらとも話せるのはなぜでしょうか。
2. LE では SMP がホストにあるのに、Classic では同じ役割がコントローラにあります。LE がホストへ移した理由は何でしょうか。
3. 新しい機器を探すとき、Classic と LE では「叫ぶ側」が逆です。それぞれどちらの機器が叫ぶのでしょうか。

::: details 答え
1. 通信できません。別の方式だからです。スマートフォンの多くは両方を載せたコントローラを持っているので、相手に合わせて使い分けられます。
2. LE のみのコントローラのコストを下げるためです。
3. Classic では探す側が Inquiry で叫びます。LE では探される側がアドバタイズで叫びます。
:::
