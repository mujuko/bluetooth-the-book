# 第3章 スタックという考え方

::: goal
- 層に分ける理由と、ホストとコントローラの役割分担を説明できる
- Classic と LE のスタックの各層の名前を大まかに言える
- データが層を下りるごとに包まれていく様子を、バイト数で追える
:::

## 3.1 なぜ層に分けるのか

通信のしくみは、複数の**層**に分けて作るのが普通です。積み重なった層の全体を**スタック**と呼びます。

::: analogy 手紙と郵便
手紙を書く人は、郵便局の仕分けや配送トラックのルートを知らなくても手紙を出せます。書く人は内容だけを考え、封筒に宛名を書いてポストに入れる。郵便局は中身を読まずに届ける。トラックの運転手は荷物の中身も宛名の詳細も気にせず、決められた道を走る。

それぞれの担当が自分の仕事にだけ責任を持ち、隣の担当との受け渡し方さえ決めておけば、全体が動きます。これが層に分ける意味です。
:::

層に分けると、たとえば電波の使い方を改良しても、アプリは変更しなくて済みます。実際に、Bluetooth 5 で LE の速度が2倍になったときも、上の層の考え方はほとんど変わっていません。

## 3.2 ホストとコントローラ

Bluetooth のスタックは、Classic でも LE でも、大きく**ホスト**と**コントローラ**の2つのブロックに分かれ、その間を **HCI** という決まった窓口がつないでいます（HCI は第5章）。

**コントローラ**は、電波に近い下の層を担当します。多くの場合、無線チップそのものです。ここで扱うのはマイクロ秒単位の仕事です。「今この瞬間に受信を始める」「受信してから 150 µs 後に返事を出す」といったことを、ソフトの都合で遅らせるわけにはいきません。

**ホスト**は、データの意味に近い上の層を担当します。スマホなら OS の一部として動くソフトウェアです。こちらはミリ秒単位でのんびり動いても問題ありません。

この分離のおかげで、メーカーの異なるチップと OS を組み合わせられます。スマートフォンの OS は、搭載チップの中身を知らなくても HCI 経由で命令できます。

ただし、ホストとコントローラは論理的な区分で、物理的に別のチップである必要はありません。安価な小型機器では、1つのチップの中にホスト、コントローラ、アプリのすべてが入っていることもよくあります。

::: bio
ホストとコントローラの関係は、脳と脊髄反射に少し似ています。熱いものに触れて手を引っ込めるとき、判断は脳まで上がらず、脊髄の回路で素早く処理されます。同じように、無線のタイミング制御はコントローラの中だけで完結します。ホストは方針を決めて伝えるだけです。
:::

どちらの図でも GAP を縦長に描いたのは、GAP がデータを運ぶ層というより、発見や接続の手順を定めて下の層を指揮する役割を持つからです。

2つの図を見比べると、違いの要点が見えてきます。

- **ペアリングの担当**：Classic ではコントローラのリンクマネージャが行い、LE ではホストの SMP が行います。LE は、LE だけのコントローラを安く作れるように、この仕事をホストへ移しました
- **相手の機能の調べ方**：Classic は SDP で「どのプロトコルでつなげばよいか」を調べ、用途ごとに別のプロトコルへ進みます。LE は ATT と GATT の「表」という共通の形で、データそのものを読み書きします

違いの全体は、第33章で表にまとめます。

## 3.4 OSI 参照モデルとの関係

ネットワークの教科書には、通信を7層に分けた OSI 参照モデルが出てきます。Bluetooth のスタックはこの全層にまたがっていて、無線の物理的な話からアプリとのやり取りまでを1つの規格の中で定義しています。他の無線規格には下の2層だけを定めるものも多いので、これは大きな特徴です。

全部を自分で定義しているおかげで、他の標準化団体の都合に左右されず、規格を進化させられます。

::: se
LE で大ざっぱに言えば、物理層とリンク層が Ethernet、L2CAP が TCP/UDP のポートによる振り分け、ATT と GATT が HTTP と REST API のような立ち位置です。ただし IP に相当する「ネットワークをまたぐ経路制御」の層はありません。あくまで直接電波が届く相手と話すための技術です。
:::

## 3.5 データは包まれながら下りていく

具体的な数字で層の働きを見てみましょう。ここでは LE の心拍計が「心拍数 72」をスマホに送る場面を例にします。データの本体はたった2バイトです（1バイトが付加情報、1バイトが心拍数。第28章で詳しく見ます）。Classic のヘッドホンに音楽が届くときの同じ追跡は、第17章で行います。

このデータは層を下りるたびに、その層の情報（**ヘッダ**）を付け足されていきます。封筒に封筒を重ねていくようなものです。

合計すると 1 + 4 + 2 + 4 + 3 + 2 + 3 = 19 バイト、つまり 152 ビットです。最も標準的な 1 Mb/s の方式なら、

<div class="formula">152 ビット ÷ 1 Mb/s = 152 マイクロ秒</div>

で送信が終わります。1秒のうち 0.15 ミリ秒しか電波を使いません。この短さが、LE の電池が長もちする秘密の1つです（第18章）。

なお、暗号化された接続ではさらに改ざん検知用の 4 バイトが加わり、23 バイトになります。

## 3.6 覚えておきたい言葉

仕様書を読むと必ず出会う言葉を3つ紹介します。

**PDU（Protocol Data Unit）**　ある層が相手の同じ層とやり取りするデータのまとまりです。図3-4 の各段が、それぞれの層の PDU にあたります。

**SDU（Service Data Unit）**　ある層が上の層から預かったデータのことです。その層にとっては中身を問わない荷物です。同じデータが、上の層から見れば PDU で、下の層から見れば SDU になります。

**MTU（Maximum Transmission Unit）**　その層が一度に扱えるデータの最大サイズです。大きなデータを送るときは、MTU に収まるように分割します（第13章、第26章）。

::: primer
- **§5.1 High-level architecture**：OSI 参照モデルの図と、Mesh がスタックにどう載るかの図があります
- **§5.2 The layers at a glance**：各層の責任を1段落ずつまとめた表。本章の LE の表のより詳しい版です
- **LC3 コーデック**：LE Audio で使う音声コーデックは、スタックの一部ではないものの、ホストかコントローラのどちらかに実装されると説明されています（本書では第24章で触れます）
:::

::: spec
- **ARCH §2**：コアシステムの全体の構造と、ホストとコントローラについての前提。末尾には適合試験のしくみ（Upper Tester と Lower Tester）の説明がある
- **ARCH §2.1**：ホストとコントローラの各ブロックの説明。LE で SMP をホストに置いた理由もここにある
:::

## まとめ

- スタックはホスト（上位の層、ソフト）とコントローラ（下位の層、チップ）に分かれ、HCI でつながっている。Classic も LE も同じ骨組みである
- 時間に厳しい仕事はコントローラが引き受け、データの意味はホストが扱う
- Classic はペアリングをコントローラで、LE はホストで行う。サービスの調べ方も、SDP と GATT で違う
- データは層を下りるごとにヘッダで包まれる。2バイトのデータも空中では19バイトになる

## 確認問題

1. 「受信後 150 µs で返事を送る」という仕事は、ホストとコントローラのどちらの担当でしょうか。理由も答えてください。
2. 図3-4 のパケットを 2 Mb/s の方式で送ると、何マイクロ秒かかるでしょうか（プリアンブルの違いは無視してかまいません）。
3. L2CAP の立場から見て、ATT の PDU は PDU と SDU のどちらでしょうか。
4. Classic ではコントローラにあるペアリングの仕事を、LE がホストへ移したのはなぜでしょうか。

::: details 答え
1. コントローラです。ホストのソフトは OS の都合などで動作が遅れることがあり、マイクロ秒単位の正確さは保証できません。
2. 152 ÷ 2 = 76 µs です。
3. SDU です。L2CAP にとって、上の層から預かった荷物だからです。
4. LE だけのコントローラを安く作れるようにするためです。
:::
