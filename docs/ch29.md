# 第29章 GAP：見つけて、つながるための作法

::: goal
- GAP の4つの役割を説明できる
- 発見のモードと接続のモードを区別できる
- アドバタイズのデータのバイト列を読み解ける
:::

**GAP**（Generic Access Profile）は、「機器どうしがどうやって見つけ合い、どうやって接続するか」という作法を定めた部分です。アドバタイズやスキャンの実際の動作はリンク層が行いますが、「どういう目的の時にどの動作を、どう組み合わせるか」を決めているのが GAP です。

## 29.1 4つの役割

GAP は機器の役割を4つ定義しています。

| 役割 | できること | 無線機能 | 例 |
|---|---|---|---|
| **ブロードキャスタ** | アドバタイズで一方的に発信する | 送信（受信は任意） | ビーコン |
| **オブザーバ** | アドバタイズを受信するだけ | 受信（送信は任意） | ビーコンの受信機 |
| **Peripheral** | 接続される | 送受信 | 心拍計 |
| **Central** | 接続を申し込む | 送受信 | スマホ |

ブロードキャスタとオブザーバは接続せず、Peripheral と Central は接続を前提とします。1台の機器が複数の役割を兼ねることもよくあります。

注意したいのは、**「Central」「Peripheral」という言葉はリンク層にもあった**ことです（第20章）。同じ言葉ですが意味が違います。リンク層の用語は「ある接続でどちら側か」を表し、GAP の用語は「機器がどんな機能を持つか」を表します。

## 29.2 発見のモード

機器がアドバタイズをしているとき、それを「発見してほしい」のかどうかを表すのが発見のモードです。

| モード | 意味 |
|---|---|
| 非発見 | 発見の手順では無視される |
| 限定発見 | 限られた時間（最大3分）だけ発見できる。「今ボタンを押したばかり」のような機器 |
| 一般発見 | 期限なしに発見できる |

機器がどのモードかは、アドバタイズのデータの中の **Flags** という項目で分かります。スキャンする側は、限定発見の機器を一覧の上に出す、といった扱いができます。ユーザーが操作した直後の機器である可能性が高いからです。

Classic でも、発見できるかどうかと接続できるかどうかは、別々のスイッチとして決められていました（[第8章](./ch08)）。考え方は LE の GAP も同じです。

::: warning 非発見モードは隠れ身の術ではない
非発見モードでも、パケットは電波として空中に出ています。発見の手順が無視するだけで、誰でも受信できます。**これはセキュリティの機能ではありません。**
:::

## 29.3 接続のモードとアドバタイズの種類

接続を受け付けるかどうか、スキャン要求を受け付けるかどうか、特定の相手に向けたものかどうか。第21章で見た PDU の種類は、これらの組み合わせに対応しています。

| | 全員向け | 特定の相手向け |
|---|---|---|
| **接続可・スキャン可** | `ADV_IND` | |
| **接続可・スキャン不可** | | `ADV_DIRECT_IND` |
| **接続不可・スキャン可** | `ADV_SCAN_IND` | |
| **接続不可・スキャン不可** | `ADV_NONCONN_IND` | |

拡張アドバタイズでは、PDU の種類ではなく **AdvMode** というヘッダの欄で同じことを表します。

特定の相手向けのパケットには、相手のアドレスの欄があり、他の機器はそれを無視します。

## 29.4 アドバタイズのデータの中身

アドバタイズの本体（**AdvData**）は、次の形式の項目を並べたものです。

<div class="formula">長さ（1バイト）＋ 種類（1バイト）＋ 値</div>

長さには「種類」の1バイトも含みます。項目の種類を **AD タイプ**といい、**Core Specification Supplement** という文書に定義されています。心拍計のアドバタイズの例を読み解いてみましょう。

```
02 01 06  03 03 0D 18  05 09 48 52 4D 31
```

| 項目 | 読み方 |
|---|---|
| `02 01 06` | 長さ2、種類 Flags。値 `0x06` は「一般発見モード」で「Classic 非対応」 |
| `03 03 0D 18` | 長さ3、種類「16ビット UUID の完全な一覧」。値はリトルエンディアンなので `0x180D`（心拍サービス） |
| `05 09 48 52 4D 31` | 長さ5、種類「完全な機器名」。値は文字コードで `HRM1` |

合計で13バイトです。レガシーの31バイトの中に、あと18バイトの余裕があります。

よく使う AD タイプを挙げておきます。

| 番号 | 意味 |
|---|---|
| `0x01` | Flags |
| `0x02` / `0x03` | 16ビット UUID の一覧（不完全／完全） |
| `0x08` / `0x09` | 機器名（短縮／完全） |
| `0x0A` | 送信電力 |
| `0x16` | サービスのデータ（16ビット UUID つき） |
| `0xFF` | メーカー固有のデータ（ビーコンなどで使う） |

スマホのアプリが「心拍サービスを持つ機器だけ」を一覧にできるのは、接続する前にこの UUID の一覧が読めるからです。これがアドバタイズに UUID を入れておく理由です。

## 29.5 スキャンのおすすめ

コア仕様（GAP）は、発見に関わる機器に向けて、次のことを勧めています。

- 発見する側は、対応しているすべての PHY でスキャンすること
- 拡張アドバタイズを使う側は、レガシーのアドバタイズも並行して出すこと（レガシーしか聞かない機器もあるため）

## 29.6 その他の担当範囲

GAP は発見と接続以外にも、次のことを定めています。

- **定期アドバタイズ**の開始と同期の手順、PAST（第23章）
- **アイソクロナス放送**の手順（第24章）
- **セキュリティ**のモードとレベル、手続き（第30章）
- **ユーザーインタフェース**の表記の基準

::: primer
- **§14.3〜14.5**：発見モード、接続モード、指向性の組み合わせをまとめた図（図75）。拡張アドバタイズでの Flags の位置
- **§14.3**：パッシブとアクティブのスキャンが、発見の手順でどう許可されるかの説明
- **§14.7**：GAP のセキュリティの手順（コア仕様 Vol.3 Part C へのポインタ）
- **§14.8, 14.9**：定期アドバタイズとアイソクロナス放送の GAP の手順
:::

## まとめ

- GAP は発見と接続の作法を定める。動作そのものはリンク層が担当する
- 役割はブロードキャスタ、オブザーバ、Peripheral、Central の4つ
- 発見のモードは Flags で伝える。非発見は隠れているわけではない
- AdvData は「長さ＋種類＋値」の並びで、接続前に機器の能力を伝えられる

## 確認問題

1. 次のアドバタイズのデータを読み解いてください：`02 01 04  03 03 0F 18`
2. Bluetooth のビーコンを受信するだけの専用機は、GAP のどの役割でしょうか。
3. 「非発見モードにしておけば、機器の存在は誰にも知られない」という主張は正しいでしょうか。

::: details 答え
1. 最初の項目は Flags で、値 `0x04` は `00000100` なので「Classic 非対応」のビットだけが立っています（発見のビットはどちらも立っていないので非発見モード）。次の項目は16ビット UUID の完全な一覧で、値は `0x180F`（電池サービス）です。
2. オブザーバです。
3. 正しくありません。パケットは誰でも受信できます。隠すことを目的とする機能ではありません。
:::
