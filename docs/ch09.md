# 第9章 アイソクロナス通信と音

::: goal
- デジタル音声の基本（サンプリング、ビット深度、コーデック、フレーム）を説明できる
- 「時間に縛られたデータ」とは何かを説明できる
- CIS と BIS の違いを説明できる
- 左右のイヤホンで音がずれないしくみを説明できる
- ISOAL が必要になる理由を説明できる
:::

LE はもともと小さなデータを少しずつ送る技術でしたが、Core 5.2 で音声を運ぶ機能が加わりました。**LE Audio** と呼ばれる新しいワイヤレス音声の土台です。この章ではまず音のデジタル化を復習し、次に LE の工夫を見ていきます。

## 9.1 音をデジタルにする

音は空気の振動で、その波形は連続的に変化しています。これを数字の列にするには、一定の間隔で値を測ります。これが**サンプリング**です。

音質を決める数字は2つあります。

- **サンプリング周波数**：1秒に何回測るか。CD は 44.1 kHz、つまり1秒に44100回
- **ビット深度**：1回の測定を何ビットで記録するか。8ビットなら 256 段階、24ビットなら約1678万段階

では、どれくらいのデータ量になるでしょうか。44.1 kHz、24ビット（3バイト）で3分（180秒）の曲を1チャンネル分だけ計算してみます。

<div class="formula">44100 回/秒 × 3 バイト × 180 秒 ≒ 2400 万バイト（約 24 MB）</div>

速さに直すと、1チャンネルで約 1.06 Mb/s です。第4章の表で LE 1M のアプリが使える速さは約 800 kb/s でした。**生の音声は、そもそも LE の無線に収まりません。**

## 9.2 コーデックとフレーム

そこで登場するのが、音声データを圧縮する**コーデック**です。LE Audio の標準は **LC3**（Low Complexity Communication Codec）で、音源によって差はありますが、元のデータの4分の1以下にできます。

コーデックは音のパターンを利用して圧縮します。ごく単純に説明すると、無音で 0 が60個並んでいるなら「0 が60個」と書くだけで済みます（実際の LC3 はずっと高度で、人の耳の特性も利用します）。パターンを見つけるには、ある程度まとまったサンプルが必要です。一度にまとめて処理するサンプルの区切りを**フレーム**と呼びます。

フレームの長さは時間で表します。10 ms や 7.5 ms がよく使われます。44.1 kHz で 10 ms なら 441 サンプルです。

<div class="formula">マイク → サンプリング → コーデックで圧縮 → フレームごとに無線で送信<br>→ 受信 → コーデックで展開 → スピーカー</div>

## 9.3 時間に縛られたデータ

ここで第7章の接続を思い出してください。LE-ACL は確実にデータを届けますが、再送のために**いつ届くかは保証しません**。心拍数なら少し遅れても問題ありません。しかし音声は違います。再生の予定時刻を過ぎて届いたデータには、もう意味がありません。

こうしたデータのための通信を**アイソクロナス通信**といいます（iso は「同じ」、chrono は「時間」の意味です）。特徴は2つです。

**データには有効期限がある**　期限を過ぎたデータは、未送信であっても捨ててしまいます。古いデータにこだわって新しいデータを遅らせることはしません。音が一瞬欠けても、遅れ続けるよりはましだからです。

**複数の受信者が同時に処理できる**　左右のイヤホンで音をそろえるしくみが組み込まれています（9.5節）。

データは**ストリーム**で流れ、関連するストリームを束ねた**グループ**を作ります。方式は2つあります。

| | CIS（Connected Isochronous Stream） | BIS（Broadcast Isochronous Stream） |
|---|---|---|
| 接続 | あり | なし |
| 方向 | 双方向 | 一方向 |
| 確認応答 | あり | なし |
| グループの名前 | CIG | BIG |
| 1グループの最大本数 | 31 | 31 |
| 例 | イヤホンで音楽や通話 | 公共の場の音声放送 |

## 9.4 CIS：接続型のストリーム

CIS を作るには、まず普通の LE-ACL 接続が必要です。ACL には2つの役目があります。ひとつは制御の PDU をやり取りする連絡路、もうひとつは CIS のタイミングを決める基準です。セントラルが CIS を申し込み（`LL_CIS_REQ`）、ペリフェラルが答え（`LL_CIS_RSP`）、セントラルが確定します（`LL_CIS_IND`）。

できあがった CIS は ACL とは別に動きますが、もとの ACL を切ると CIS も終わります。

イベントは **ISO 間隔**ごとに来ます。1回のイベントは複数の**サブイベント**に分かれ、それぞれがセントラルの送信（T）とペリフェラルの返事（R）の組です。うまくいかなければ次のサブイベントで、別のチャネルを使ってやり直せます。

再送の余裕を決める重要なパラメータが3つあります。

| 名前 | 意味 | 大きくすると |
|---|---|---|
| NSE（Number of Subevents） | 1イベントのサブイベントの数 | 再送の機会が増えるが無線の時間が増える |
| BN（Burst Number） | 1イベントで新たに送るデータの個数 | 通信量が増える |
| FT（Flush Timeout） | データを何回のイベントまで再送してよいか | 確実に届くが遅延が増える |

FT の期限が来たデータは、届いていなくても捨てられます（フラッシュ）。これが「有効期限」の実体です。

## 9.5 左右の音をそろえる

左右のイヤホンに音を送る場面を考えます。無線は一度に1つしか送れないので、まず左に送り、次に右に送るしかありません。そのままでは、右の音が遅れます。

解決法は単純です。**先に受け取ったほうが長く待つ**のです。

<figcaption>図9-3 同期遅延。ストリームごとに別の待ち時間を設定し、同じ時刻に再生する</figcaption>

グループ全体の遅延の値（`CIG_Sync_Delay`）に対して、各ストリームには個別の値（`CIS_Sync_Delay`）が設定されています。グループの最初のストリームほど長く待ち、最後のストリームほど短く待ちます。こうして、2つのイヤホンは互いに通信しなくても同時に鳴らせます。さらにプロファイルが、デコードの処理時間などを見込んだ遅延を上乗せすることもあります。

::: bio
左右の耳に音が届く時間のわずかな差は、脳にとって音の方向を知る手がかりです（第10章でもう一度触れます）。だからこそ、イヤホンの左右で再生がずれると音の定位がおかしくなります。Bluetooth が左右の同期に細かくこだわる理由のひとつです。
:::

## 9.6 BIS：放送型のストリーム

空港の案内放送を、多数の人のイヤホンに同時に届けたいとしましょう。全員と接続するのは現実的ではありません。そこで使うのが **BIS** です。

BIS は一方向の放送で、確認応答がありません。確実性を補うために、同じデータを**無条件に何度も繰り返し**ます。返事の枠を取る必要がないので、同じ時間に CIS の2倍のサブイベントを詰め込めます。繰り返しは、前回の送信から 6 MHz 以上離れたチャネルで行うので、特定のチャネルの混信で全滅しにくくなっています。

受信者はどうやって放送を見つけるのでしょう。BIS のパラメータ（ストリームの数、間隔など）をまとめた **BIGInfo** が、第8章の定期アドバタイズに載って流れています。受信者は定期アドバタイズに同期し、BIGInfo を読み、BIS を聞き始めます。この同期には電力がかかるので、PAST でスマホに代わりに探してもらう方法もあります。

音をそろえる方法は CIS と似ています。受信者は BIGInfo の値から、再生までの待ち時間を計算します。

暗号化もできます。ペアリングは不要で、代わりに **Broadcast Code** という合言葉を受信者に配ります（紙に印刷された QR コードで渡すなど、方法は自由です）。

::: extra Auracast
BIS を使った音声放送を、Bluetooth SIG は Auracast という名前で展開しています。空港や駅の案内、スポーツバーのテレビ音声、補聴器への放送などが応用例です。LE Audio の上位の規格（BAP など）は原本の範囲外で、Nick Hunn 著の eBook が原本の参考文献に挙げられています。
:::

## 9.7 ISOAL：フレームの長さの違いを吸収する

最後に、スタックの中の小さな層 **ISOAL**（Isochronous Adaptation Layer）を紹介します。

送信側のコーデックが 10 ms のフレームを作るのに、無線は 7.5 ms ごとに送る、ということがあります。このように、上の層のデータ（SDU）の時間の単位と、リンク層の PDU の時間の単位が合わないときに、橋渡しをするのが ISOAL です。

**割り切れる場合（unframed、アンフレーム）**　10 ms のフレームを 5 ms ずつに分けるなら話は簡単です。単純に分けて並べるだけです。各 PDU にはフレームの断片が1つだけ入り、ヘッダには「先頭、途中、末尾」の印がつきます。

**割り切れない場合（framed、フレーム）**　10 ms と 7.5 ms のように割り切れないと、1つの PDU に別のフレームの断片がまたがって入ります。そこで断片ごとに短いヘッダをつけ、「ここからフレーム2の始まり」という印と、タイミングのずれの情報を記録します。

言葉がややこしいので整理しておきましょう。

| データの種類 | 分ける処理 | 組み立てる処理 |
|---|---|---|
| アンフレーム | フラグメンテーション | リコンビネーション |
| フレーム | セグメンテーション | リアセンブリ |

リンク層の PDU の **LLID** という欄を見れば、どちらの形式かが分かります。

::: primer
- **§7.8.5.2.3**：CIG のスケジュール（シーケンシャルとインターリーブ）、Sub_Interval（400 µs 以上）
- **§7.8.5.2.5**：CIS 作成の PDU に含まれるパラメータ（CIS_Offset など）
- **§7.8.5.3**：BIG のパラメータ（BIS_Spacing, BIG_Sync_Delay）、制御用サブイベント、BIGInfo の詳細（ACAD 欄）
- **§9.1**：音声のサンプリングとビット深度の解説、音声処理の流れの図
- **§9.3, 9.4**：ISOAL の処理の図解
- **§14.9**：GAP が定める放送の手順
:::

## まとめ

- 音声はサンプリングで数字にし、コーデックで圧縮し、フレーム単位で送る
- アイソクロナス通信では、データに有効期限があり、期限を過ぎたものは捨てる
- 接続型の CIS は再送で確実性を高め、放送型の BIS は無条件の繰り返しで補う
- 先に受信したストリームほど長く待つことで、同時に再生する
- ISOAL はフレームの時間と無線の時間の違いを吸収する

## 確認問題

1. 48 kHz、16ビットの音声1チャンネルを生のまま送ると、何 Mb/s になるでしょうか。
2. LE-ACL の再送と CIS の再送の、いちばん大きな考え方の違いは何でしょうか。
3. FT を大きくすると、音声品質と遅延にどんな影響があるでしょうか。
4. 図9-3 で、もし右耳のストリームが先に送られるようにしたら、左右の待ち時間はどうなるでしょうか。

::: details 答え
1. 48000 × 16 = 768000 b/s = 0.768 Mb/s です。
2. LE-ACL は届くまで再送を続け、遅れは気にしません。CIS は期限内でのみ再送し、期限が過ぎたら捨てます。
3. 再送の機会が増えるので音切れは減りますが、そのぶん再生までの遅延が増えます。
4. 右耳が長く待ち、左耳が短く待つようになります。先に受信したほうが長く待つ、という関係は同じです。
:::
