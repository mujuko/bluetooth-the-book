# 第24章 ACL：確実に運ぶ

::: goal
- ARQN と SEQN の2つのビットで再送が動くしくみを追える
- ヘッダ、ペイロード、L2CAP という誤り対策の層を説明できる
- 流量調整のしくみが複数ある理由を説明できる
- フラッシュとは何か、なぜ音楽で必要なのかを説明できる
:::

**ACL** は Classic の主力の運び手です。LMP の制御メッセージも、L2CAP のデータも、音楽も、ファイルも、すべて ACL の上を流れます。ここでは「確実に運ぶ」ためのしくみを見ていきます。

## 24.1 たった2ビットの再送

無線は必ず失敗します。パケットが壊れたら送り直す必要があります。受信側が結果を伝え、送信側が再送するこのやり方を **ARQ**（Automatic Repeat reQuest）と呼びます。

ヘッダの中で再送に使うビットは2つだけです。

| ビット | 名前 | 意味 |
|---|---|---|
| ARQN | 確認 | 1 なら ACK（届いた）、0 なら NAK（届いていない） |
| SEQN | 順序 | 新しいデータのたびに 0 と 1 を反転する |

返事は、次の自分のパケットのヘッダに便乗させます。パケットの番号を覚える必要がないので、仕様はこれを「番号なしの ARQ」と呼びます。Peripheral は直後のスロットで返事をするので、結果はすぐに分かります。

場面3に注目してください。確認の返事だけが失われると、送信側は再送します。でも受信側はすでに受け取っています。SEQN が前回と同じなら「これは再送だ」と分かるので、中身を捨てて ACK だけ返します。

LE の SN と NESN（[第7章](./ch07)）とよく似ています。違いは速さです。LE は次の接続イベントまで待つことがありますが、Classic の Active な接続では、次のスロットで結果が分かります。

もちろん、再送の間は相手と話す機会を消費するので、スループットは下がります。

::: bio
DNA の複製の校正機能に似ています。DNA ポリメラーゼは間違った塩基を入れると、その場で取り除いて入れ直します。さらに複製の後には、ミスマッチ修復という別の層の点検が控えています。Classic の誤り対策も、次の節で見るように何層にもなっています。
:::

## 24.2 誤り対策の層

ACL の誤り対策は、1つの強力なしくみではなく、何層かの組み合わせです。

| 層 | 対象 | しくみ | 役目 |
|---|---|---|---|
| ベースバンド | ヘッダ | 1/3 の FEC と 8 ビットの HEC | 直す、検出する（失敗ならパケットごと捨てる） |
| ベースバンド | ペイロード | 2/3 の FEC（DM の場合） | 少しの誤りを直す |
| ベースバンド | ペイロード | 16 ビットの CRC と ARQ | 検出して再送する |
| ベースバンド | ペイロード | 32 ビットの MIC（AES-CCM のとき） | 改ざんを検出する |
| L2CAP | L2CAP のフレーム | FCS と再送（設定した場合） | 下で見逃した誤りと欠落に対応する |

一番下の行には理由があります。

CRC は誤りの検出のためのチェックサムで、たまたま値が一致して誤りを見逃す可能性があります。16 ビットの CRC なら、壊れたデータがランダムに一致する確率はおよそ 6.5 万分の 1 です。短いパケットをときどき送るだけならこれで十分です。しかし、長いパケットを大量に送ると、見逃しがいつか現実の問題になります。ARCH §3.1.3.1 も、長いパケットでは未検出の誤りの確率が高すぎると指摘しています。

そこで L2CAP に、もう1段の誤り検出と再送を用意しました（[第27章](./ch27)）。一方、LE は CRC が 24 ビットと長いので、L2CAP でこの対策をする必要がありません（ARCH §3.1.3.2）。

## 24.3 流量調整

受信側の処理が追いつかないとき、送信を止める必要があります。Classic には、層ごとに流量調整のしくみがあります。

| どこで | しくみ | 止めるもの |
|---|---|---|
| パケットヘッダ | FLOW ビット | 相手からの ACL パケット全体（受信バッファがいっぱいのとき） |
| ペイロードヘッダ | FLOW ビット | L2CAP のデータ |
| HCI | チップのバッファの空きを数える方式（`HCI_Number_Of_Completed_Packets` で空きを知らせる） | ホストからコントローラへの送り込み |
| L2CAP | 窓、クレジットなど（設定した場合） | チャネルごとの流量 |

このように分かれているのは、データが通る場所ごとに詰まる可能性があるからです。チップのバッファ、HCI の通路、アプリの受信処理は、それぞれ別の理由で詰まります。

なお、パケットヘッダの FLOW で止められるのは ACL のデータだけです。POLL や NULL、SCO、eSCO は流れ続けます。

## 24.4 L2CAP のフレームを分割して運ぶ

L2CAP のフレームは最大 64 KB ほどまで大きくできますが、Classic のパケットには 1021 バイトまでしか入りません。そこで分割して運びます。受信側が組み立て直すために、ペイロードヘッダの LLID で先頭と続きを区別します。

| LLID | 意味 |
|---|---|
| `0b10` | L2CAP のフレームの先頭 |
| `0b01` | 続き |

この方式には巧妙な点があります。各パケットに L2CAP の長いヘッダを付けなくても、先頭のパケットにだけ付ければ足ります。1つのフレームを完全に送り終えるまで、同じ ACL-U に別のフレームが割り込まないからです。

## 24.5 フラッシュ：あきらめる勇気

ここまでは「届くまで再送する」話でした。でも、時間に縛られたデータでは、それが裏目に出ることがあります。

音楽を考えてみましょう。電波の悪い場所で、あるパケットの再送が続いたとします。再送している間にも、次の音のデータが生まれ続けます。もし古いデータにこだわって再送を続けたら、遅れがどんどん積み重なってしまいます。すでに再生の時刻を過ぎたデータは、届いても無駄です。

そこで、**期限が来たら古いデータを捨てて次へ進む**ことができます。これを**フラッシュ**（flush）と呼びます。

受信側は、途中まで受け取っていたフレームがあっても、次に `LLID=10` が来れば「前のフレームはあきらめたのだな」と分かります。

期限は HCI の `HCI_Write_Automatic_Flush_Timeout` で設定します。範囲は 0.625 ms から 1279.375 ms で、0 を指定すると無限大（フラッシュしない）になります。

1本の ACL に、捨ててよいデータと捨ててはいけないデータが混ざることもあります。音楽と一緒に流れるリモコンの操作を捨てるわけにはいきません。そこでホストは、L2CAP のフレームを HCI で渡すときに「自動フラッシュしてよいか」を指定します。

ARCH §3.5.2 の言葉で言えば、これが「ACL をアイソクロナスとして使う」方法です。Classic には、LE の CIS（[第9章](./ch09)）のようなアイソクロナス専用の運び方はありません。

::: tip 音が途切れる理由
ヘッドホンの音が「プツッ」と途切れるのは、再送が間に合わずにデータを捨てた（あるいは受信側の再生バッファが空になった）ときです。逆に途切れないように受信バッファを大きく取ると、音は遅れます。動画の口の動きと音がずれるのはこれが一因です。途切れと遅れはトレードオフです。
:::

## 24.6 接続の切れ目を知る

電波が届かなくなっても、無線は「切れた」と教えてくれません。そこで両者は、タイマーで監視します。自分宛てのパケットを受信するたびにタイマーをリセットし、一定時間届かなければ接続が切れたとみなします。これが**リンクスーパービジョンタイムアウト**で、既定値は 20 秒です。Sniff の間隔より長くする必要があります。

## 24.7 全員宛ての APB

Central が全員に同じものを伝えるためには、**APB**（Active Peripheral Broadcast）があります。LT_ADDR は `000` です。確認の返事がないので、信頼性を上げるために同じパケットを何回か繰り返します。

L2CAP の接続のない通信（CID `0x0002`）や、一部の LMP に使います。なお、ピコネットに相手が1台しかないなら、Central は全員宛てを普通の ACL で送ることもできます。そのほうが確認も取れて効率的です。

## まとめ

- ACL の再送は ARQN と SEQN の2ビットで動き、返事は次のパケットのヘッダに便乗する
- SEQN が前回と同じなら、受信側は中身を捨てて ACK を返す
- 誤り対策は FEC、HEC、CRC、MIC、L2CAP の何層もの組み合わせである
- 16 ビットの CRC は長いデータでは見逃しが問題になるので、L2CAP に追加の対策がある
- 流量調整はヘッダ、ペイロードヘッダ、HCI、L2CAP のそれぞれにある
- 時間に縛られたデータは、期限切れで捨てるフラッシュで遅れの積み重なりを防ぐ

## 確認問題

1. ACK が失われたとき、受信側は同じデータを2回アプリに渡してしまうでしょうか。
2. L2CAP の 2000 バイトのフレームを 2-DH5 で送ると、何パケットになるでしょうか。
3. 電波が悪い環境でも、ファイル転送は遅くなるだけで壊れないのに、音楽では音が途切れるのはなぜでしょうか。
4. LE では L2CAP の追加の誤り検出が要らないのは、なぜでしょうか。

::: details 答え
1. 渡しません。SEQN が前回と同じなので、受信側は再送だと分かり、中身を捨てて ACK だけを返します。
2. 2-DH5 は 679 バイト運べます。2000 ÷ 679 = 2.9… なので 3 パケットです。
3. ファイルは届くまで再送します。音楽には期限があるので、間に合わないデータはフラッシュして捨てるからです。
4. LE の CRC は 24 ビットと長く、見逃しの確率が十分に小さいからです。
:::
