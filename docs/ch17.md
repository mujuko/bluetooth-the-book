# 第17章 アプリを作るときの現実

::: goal
- 仕様にある機能がアプリで使えるとは限らない理由を説明できる
- 用途に合う通信の型を選べる
- 実際に LE の機器と通信し、観察する方法を知る
- 次に読むべき資料を選べる
:::

これまで規格の話をしてきました。最後に少し現実の話をしましょう。

## 17.1 仕様にある ≠ 使える

「スマホが Bluetooth 5.4 対応」と書いてあっても、5.4 の機能が使えるとは限りません。理由は3つあります。

**1. 普及に時間がかかる**　新しい仕様が出てから、チップ、OS、製品に載るまでには何年もかかります。

**2. ほとんどの機能は任意**　LE の機能の多くは実装しなくてもかまいません。「5.4 対応」は、5.4 のすべての機能を持つという意味ではありません。チップのメーカーや OS の開発者が何を入れるかを決めます。

**3. API がなければアプリからは使えない**　チップと OS のスタックが対応していても、アプリ向けの API が用意されていなければ、アプリからは使えません。

ですから、開発を始める前に次の点を確かめましょう。

- 対象機器のチップとスタックが、その機能に対応しているか
- OS のバージョンごとに API があるか
- 相手側の機器も対応しているか

## 17.2 どの通信の型を選ぶか

本書で学んだ型を、目的別に並べてみます。

| やりたいこと | 候補 | 章 |
|---|---|---|
| 1台の相手とデータを確実にやり取りする | 接続（ACL）と GATT | 第7章、第14章 |
| 機器の存在を周囲に知らせる | レガシーアドバタイズ | 第6章 |
| 短いデータを誰にでも配る | アドバタイズ（`ADV_NONCONN_IND`） | 第6章 |
| 大きめのデータを放送する | 拡張アドバタイズ | 第6章 |
| 決まった周期で多数に放送し、受信側の電力を節約する | 定期アドバタイズ | 第8章 |
| 数千台の機器を個別に低電力で制御する | PAwR | 第8章 |
| 音声を1対1や左右のペアに送る | CIS | 第9章 |
| 音声を不特定多数に放送する | BIS | 第9章 |
| 位置の方向を知る | AoA / AoD | 第10章 |
| 安全に距離を測る | Channel Sounding | 第10章 |

標準のサービスがあるなら、それを使うことを検討してください。他社のアプリや機器とつながる可能性が開けます。

## 17.3 まず観察してみよう

::: extra この節は原本の外の補足です
LE を学ぶには、実物に触れるのが一番です。特別な機材がなくても始められます。
:::

**スマホのアプリで見る**　Nordic Semiconductor の **nRF Connect for Mobile** のような汎用ツールを入れると、周囲の機器のアドバタイズを一覧でき、接続すれば GATT のサービスやキャラクタリスティックも見られます。第15章のバイト列や第14章の表を、実物で確認してみましょう。

**HCI のログを読む**　第11章で紹介した `btmon` や Android の HCI スヌープログを使えば、アプリと無線の間のやり取りが見られます。

**空中のパケットを見る**　スニファと呼ばれる専用の受信機（nRF Sniffer など）と Wireshark を使えば、電波そのものを観察できます。

## 17.4 ブラウザから心拍計につないでみる

**Web Bluetooth** を使えば、少しの JavaScript で第14章の流れを試せます。Chrome や Edge で動きます（Safari と Firefox は標準では未対応です）。HTTPS のページか localhost で、ボタンのクリックなどをきっかけに呼ぶ必要があります。

```js
async function start() {
  // アドバタイズの UUID で絞り込んで機器を選ぶ（第15章）
  const device = await navigator.bluetooth.requestDevice({
    filters: [{ services: ['heart_rate'] }]
  })

  // 接続して、サービスとキャラクタリスティックを探す（第7章、第14章）
  const server = await device.gatt.connect()
  const service = await server.getPrimaryService('heart_rate')
  const measurement = await service.getCharacteristic('heart_rate_measurement')

  // CCCD に 01 00 を書き込む（第14章）
  await measurement.startNotifications()

  // 通知が届くたびに、バイト列を解釈する（第14章）
  measurement.addEventListener('characteristicvaluechanged', (event) => {
    const value = event.target.value
    const flags = value.getUint8(0)
    const bpm = flags & 0x01 ? value.getUint16(1, true) : value.getUint8(1)
    console.log(`心拍数: ${bpm}`)
  })
}
```

たった20行ほどの裏側で、本書で学んだことのほとんどが動いています。`startNotifications()` の1行が CCCD への書き込みになり、ATT の PDU になり、L2CAP で包まれ、リンク層のパケットになって、ホッピングしながら電波として飛んでいくのです。

手元に心拍計がなければ、nRF Connect（Android 版）の GATT サーバ機能などで代用できます。

## まとめ

- 仕様の版番号は、機能の実装も API の存在も保証しない。事前に調べよう
- 目的に合わせて通信の型を選ぶ。標準のサービスがあれば活用する
- 汎用のスキャンアプリや HCI のログで、規格の話を実物で確かめられる

## 確認問題

1. 「Bluetooth 6.0 対応スマホなら Channel Sounding のアプリが作れる」は正しいでしょうか。
2. 17.4 節のコードの `flags & 0x01` は何を調べているのでしょうか。
3. 建物の中の多数の照明を1台の機器から個別に低電力で制御したいとき、候補になる通信の型は何でしょうか（Mesh を除く）。

::: details 答え
1. 正しいとは限りません。Channel Sounding は任意の機能で、チップの対応、OS の API の有無を確認する必要があります。
2. 心拍数のデータの形式です。最下位ビットが0なら1バイト、1なら2バイトです（第14章）。
3. PAwR です。
:::
