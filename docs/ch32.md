## 32.2 場面ごとに層を追う

### 場面0：起動

心拍計の電源が入ります。ホストのソフトは、心拍サービスを含む GATT の表を作ります。ATT のレベルでは、ハンドルのついた表ができあがります（[第28章](./ch28)）。次に、HCI を通してコントローラに「この内容、この間隔でアドバタイズして」と指示します（[第5章](./ch05)）。ここからはコントローラが自動で動き、ホストは休めます。

### 場面1：アドバタイズ

コントローラは、たとえば 100 ms ごとに少しランダムな遅れを足しながら、3本のチャネルに同じパケットを送ります（[第21章](./ch21)）。

パケットの先頭はプリアンブルで、続くアクセスアドレスはアドバタイズ共通の `0x8E89BED6` です（[第20章](./ch20)）。中身は「Flags」「心拍サービスの UUID」「機器名」の3項目です（[第29章](./ch29)）。電波は GFSK で周波数を上下に振りながら飛んでいきます（[第4章](./ch04)）。

一方、スマホのアプリは OS に「心拍サービスを持つ機器を探して」と頼みます。OS のホストは HCI でスキャンを指示し、コントローラはチャネルを切り替えながら耳を澄まします。やがてパケットを受信すると、CRC を確かめ、LE Advertising Report のイベントでホストに報告します。OS はそれをアプリに渡し、画面に機器名が表示されます。

### 場面2：接続

ユーザーがタップすると、スマホのコントローラはイニシエート状態になります。次にそのアドバタイズを受信した直後、同じチャネルで `CONNECT_IND` を送ります。パケットに書かれた約束を受け取った心拍計は、Peripheral になります。スマホは Central です（[第20章](./ch20)、[第22章](./ch22)）。

以後はアドバタイズのチャネルを離れ、共有した計算式に従って37本のチャネルをホッピングしながら、接続イベントごとに交互に話します。

### 場面3：接続の調整

2台のリンク層は、対応する機能を交換します。データ長やMTUを広げる交渉もよく行われます（[第26章](./ch26)）。ここで PHY を 2M に切り替えることもあります（[第19章](./ch19)）。

### 場面4：サービスディスカバリ

スマホは心拍計の持つ表を知らないので、ATT の検索で調べていきます。心拍サービスの場所、測定値の行のハンドル、CCCD のハンドルが分かります（[第27章](./ch27)、[第28章](./ch28)）。

### 場面5：購読（必要ならペアリングも）

スマホは CCCD に `01 00` を書き込みます。心拍計が「このキャラクタリスティックは暗号化が必要」と設定していれば、ここでエラーが返り、OS がペアリングの手続きを始めます（[第30章](./ch30)）。

### 場面6：心拍が届く

ここが本書のクライマックスです。心拍計のセンサが心拍数 72 を測定しました。

**ホスト側（送信）**

1. アプリが「測定値の更新」を GATT に伝える。GATT は CCCD がオンなのを確認する
2. ATT が、オペコードとハンドル `0x0012` を付けて通知の PDU を作る（5バイト）
3. L2CAP が、CID `0x0004` を含むヘッダを付ける（9バイト）
4. HCI を通じてコントローラへ渡す

**コントローラ側（送信）**

5. リンク層が、SN と NESN を含むヘッダを付ける（11バイト）。暗号化されていれば暗号化し、MIC を付ける
6. CRC を計算して付け、ホワイトニングをかける
7. 次の接続イベントの時刻まで待つ。時刻が来ると、チャネルを計算して無線を起動する
8. Central のパケットを受信した 150 µs 後に、物理層がビットを周波数の変化に変えて送信する（19バイト、1 Mb/s なら 152 µs）

**電波**

9. 電波が約 1 m の空間を、3ナノ秒ほどで飛ぶ

**スマホ側（受信）**

10. 物理層がプリアンブルで同調し、周波数の変化をビットに戻す
11. リンク層がアクセスアドレスを確かめ、ホワイトニングを戻し、CRC を確かめる
12. NESN を反転させる。次のパケットで心拍計は「届いた」と知る
13. HCI でホストへ渡す
14. L2CAP が CID `0x0004` を見て ATT へ渡す
15. ATT がハンドル `0x0012` を見て、GATT が「心拍数の測定値」だと対応づける
16. OS がアプリを呼び出す
17. アプリがフラグを見て、`0x48` を 72 と解釈し、画面に表示する

これが、1秒に1回、ランニング中ずっと繰り返されます。

### 場面7：邪魔が入ったら

近くで電子レンジが動き始めました。ある接続イベントでパケットが壊れます。CRC が合わず、受信側は確認を返しません。送信側は次の機会に別のチャネルで再送します（[第22章](./ch22)）。

あるチャネル帯で失敗が続くと、Central はチャネルマップを更新して避けるようになります。ユーザーは何も気づきません。

### 場面8：別れ

ランニングが終わり、スマホがアプリで切断を選ぶと、リンク層の切断の手続きが行われます。心拍計が圏外に出た場合は、スーパービジョンタイムアウトで切断とみなされます。心拍計はまたアドバタイズに戻り、次の出会いを待ちます。

## 32.3 スタックをもう一度眺める

旅の始めに見た第3章の図3-3 を、もう一度見てください。今度は、それぞれの箱の中で何が起きているかが想像できるのではないでしょうか。

| 層 | 心拍計の物語での役割 |
|---|---|
| アプリ | センサの値を読む。画面に出す |
| GATT | 「0x0012 は心拍数の測定値」という意味づけ |
| ATT | 通知の PDU を運ぶ |
| SMP | 必要なときにペアリングを行う |
| GAP | 発見と接続の作法 |
| L2CAP | CID で ATT に振り分ける |
| HCI | チップとの受け渡し |
| リンク層 | タイミング、ホッピング、再送、CRC |
| 物理層 | ビットを周波数の変化に変える |

## 32.4 おわりに

2バイトのデータを送るのに、こんなにたくさんのことが起きています。しかも、コイン電池1個で1年も動きます。

その秘密は、一言でいえば第18章で述べたとおり「できるだけ無線を使わない」です。そのために、タイミングの約束、短いパケット、役割の非対称、層の分担といった工夫が積み重なっています。それぞれの工夫には理由があり、理由が分かれば、覚えることはずっと減ります。

次は実物に触れてみてください。第31章のツールで周りの機器を観察すれば、きっと新しい発見があるはずです。もし原本やコア仕様を開いてみて、以前より読めるようになっていると感じたら、この本の役目は果たせたことになります。

LE の話はここまでです。最後の[第33章](./ch33)では、第II部の Classic と LE を並べて、2つの Bluetooth を振り返ります。

## 最後の確認問題

1. アドバタイズの本体の中の `0D 18` と、通知の PDU の中の `0x0012`。どちらも機器に関する番号ですが、それぞれ何を表していて、どう違うのでしょうか。
2. 場面6の手順2〜8で、心拍計のホストはどの時点で眠ることができるでしょうか。
3. 暗号化された接続で、場面6のパケットは全部で何バイトになるでしょうか。1 Mb/s なら何マイクロ秒でしょうか。
4. 友達に「Bluetooth はなぜ電池が長持ちするの？」と聞かれたら、どう答えますか。30秒で説明してください。

::: details 答え
1. `0D 18` はリトルエンディアンの UUID `0x180D` で、「心拍サービス」というデータの**種類**を表します。どの心拍計でも同じです。`0x0012` はこの機器の表の中の**行番号**（ハンドル）で、機器によって違います。
2. コントローラに渡した後（手順4の後）です。電波の細かいタイミングはコントローラの仕事です。
3. 19 バイトに MIC の 4 バイトを足して 23 バイト、184 ビットなので 184 µs です。
4. たとえば：「無線を使うのに一番電気を使うから、ほとんどの時間は無線を切って眠っているんだ。次に通信する時刻を相手と約束しておいて、その一瞬だけ起きる。データも小さいから、0.2ミリ秒くらいで送り終わる。しかも大変な作業はスマホに任せている。」
:::
