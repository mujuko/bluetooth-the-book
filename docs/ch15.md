# 第15章 ペアリングと暗号

::: goal
- セキュリティの5つの機能（ペアリング、ボンディング、認証、暗号化、完全性）を区別できる
- 古いペアリングが破られやすかった理由を説明できる
- Secure Simple Pairing の4つの方式と選ばれ方を説明できる
- Classic のセキュリティの3つの世代を説明できる
:::

ヘッドホンの最初の接続では、画面に「ペアリングしますか」と表示されます。2回目からは何も聞かれません。この裏で何が起きているのかを見ていきます。ここで出てくる考え方の多くは、LE のセキュリティ（[第30章](./ch30)）でも共通です。

## 15.1 5つの機能

| 機能 | 何をするか |
|---|---|
| **ペアリング** | 共通の秘密の鍵を作る手続き |
| **ボンディング** | 鍵を保存して、次回も使う |
| **機器認証** | 相手が同じ鍵を持っていることを確かめる |
| **暗号化** | 内容を盗み聞きされないようにする |
| **完全性の保護** | 内容を書き換えられないようにする |

2回目から確認が要らないのは、ボンディングで鍵を保存しているからです。接続のたびに、鍵を持っていることを確かめ（認証）、その鍵から暗号化の鍵を作り直します。

::: bio
ボンディングは免疫記憶に似ています。一度出会った相手の情報を記憶細胞に残しておけば、次からは初回のような長い手続きなしで反応できます。ただし、Classic の鍵は相手の機器と1対1で結びつく点が違います。
:::

**LE との大きな違いは、ペアリングを担当する場所**です。LE ではホストの SMP が行いますが、Classic では**コントローラのリンクマネージャが LMP で行います**。ホストは「ユーザーが Yes と言った」といった情報を渡すだけです。

## 15.2 3つの世代

Classic のセキュリティは、時代とともに作り直されてきました。今の仕様にも、互換のために3世代すべてが残っています。

| 世代 | 鍵の生成 | 認証 | 暗号化 | 完全性 |
|---|---|---|---|---|
| Legacy Pairing | SAFER+（E21, E22） | SAFER+（E1） | E0 | なし |
| Secure Simple Pairing（Core 2.1） | P-192 の ECDH、SHA-256、HMAC-SHA-256 | SAFER+（E1） | E0 | なし |
| Secure Connections（Core 4.1） | P-256 の ECDH、HMAC-SHA-256 | HMAC-SHA-256 | **AES-CCM** | **AES-CCM** |

ここで出てきた E0 は、ストリーム暗号の一種です。CRC にも多少の誤り検出の能力はありますが、攻撃者は CRC を簡単に計算し直せるので、改ざんの防止にはなりません。完全性が守られるのは AES-CCM の世代からです。

## 15.3 第1世代：Legacy Pairing の弱点

古い方式は PIN コードを入力します。両方の機器に同じ番号を入れ、それをもとに鍵を作ります。ところが、ここに根本的な問題がありました。

<div class="formula">鍵の材料の中で、秘密なのは PIN だけ</div>

ほかの材料（アドレス、乱数）は電波を流れてきます。ということは、攻撃者がペアリングと1回の認証のやり取りを**録音**しておけば、あとは自分のパソコンで PIN を総当たりできるのです。正しい PIN を試すと、録音と計算が一致します。相手と通信する必要はありません。

4桁の PIN は1万通りしかありません。しかも「0000」や「1234」のような固定値の製品も多くありました。これではパソコンで一瞬です。

| PIN や方式 | 強さ（秘密のビット数） |
|---|---|
| 4桁の数字の PIN | 約 13 ビット |
| 16桁の数字の PIN | 約 53 ビット |
| 16文字の英数字の PIN | 約 95 ビット |
| SSP（P-192） | 約 96 ビット |
| SSP（P-256） | 約 128 ビット |

長い PIN なら強くなりますが、人が16文字も入力するのは現実的ではありません。

## 15.4 第2世代：Secure Simple Pairing

Core 2.1 の **Secure Simple Pairing（SSP）** は、公開鍵暗号（ECDH）でこの問題を解決しました。

2台は公開鍵を交換するだけで、**電波を聞いている人には計算できない共通の秘密**を作れます。盗聴者の目の前で秘密を作るとは不思議ですが、次のたとえで考えると分かりやすいでしょう。

::: analogy 絵の具の混色
AさんとBさんが、共通の色の絵の具を決めます（公開情報）。それぞれ、自分だけの秘密の色を混ぜて、混ぜた後の色を相手に送ります。受け取った相手は、そこに自分の秘密の色をさらに混ぜます。すると両者の手元には、同じ「共通色＋Aの秘密＋Bの秘密」の色ができます。盗聴者は混ぜた後の色しか見ていません。絵の具は混ぜるのは簡単ですが、分離するのは困難なので、秘密の色は分かりません。
:::

実際の ECDH では、絵の具の代わりに楕円曲線という数学の道具を使います。録音しておいて総当たり、という攻撃はできなくなります。しかも、**ユーザーが何も入力しなくても**この強さが得られます。

SSP の名前の Simple には、「ユーザーの手間を減らす」という意味が込められています。

ただし、ECDH だけでは防げない攻撃があります。2台の間に割り込んで、それぞれと鍵を作る**中間者攻撃（MITM）** です。これを防ぐには、ユーザーが「本当にこの相手か」を確かめる必要があります。その方法が次の4つです。

### 4つの方式

| 方式 | ユーザーの操作 | MITM への耐性 | 例 |
|---|---|---|---|
| **Numeric Comparison** | 両方の画面の6桁の数字を見比べて Yes | あり | スマホとパソコン |
| **Passkey Entry** | 片方に表示された6桁を、もう片方で入力 | あり | パソコンとキーボード |
| **Just Works** | 確認するだけ（または何もなし） | **なし** | スマホとヘッドホン |
| **Out of Band** | NFC のタッチなど、Bluetooth 以外の手段 | 手段による | NFC 対応スピーカー |

どれになるかは、**2台の入出力の能力（IO Capability）** で自動的に決まります。ペアリングの最初に、この能力を伝え合います。

| 2台の能力 | 選ばれる方式 |
|---|---|
| 両方に画面と Yes / No のボタン | Numeric Comparison |
| 片方にキーボード、もう片方に画面 | Passkey Entry |
| どちらかに入出力がない | Just Works |

ヘッドホンには画面がないので、ほとんどの場合 Just Works です。この方式は MITM を防げませんが、盗聴には強いままです。「固定の PIN よりはずっとよい」と Architecture 編も述べています。

### 6桁の数字は秘密ではない

SSP の6桁の数字は、Legacy の PIN とは意味がまったく違います。

| | Legacy の PIN | SSP の6桁 |
|---|---|---|
| 位置づけ | 鍵の**材料** | 計算の**結果**（または鍵とは独立の確認） |
| 知られると | 鍵が計算される | 鍵は計算できない |
| 総当たり | 録音からオフラインで可能 | MITM の成功は1回につき100万分の1 |

Numeric Comparison の場合、攻撃者が割り込んでいれば、2つの画面の数字は（100万分の1の確率を除いて）一致しません。1回失敗すれば接続できないので、攻撃者には何度も試す機会がありません。だから6桁で十分なのです。

### SSP の5つの段階

| 段階 | 内容 |
|---|---|
| 準備 | 入出力の能力の交換（ここで方式が決まる） |
| 1 | 公開鍵の交換 |
| 2 | 認証ステージ1（**方式ごとにここだけ違う**） |
| 3 | 認証ステージ2（交換した値の確認） |
| 4 | リンクキーの計算 |
| 5 | LMP での認証と暗号化の開始 |

### HCI から見ると

実際の手続きはチップの中で進みますが、ユーザーの判断は必要です。そこでコントローラはホストへ問い合わせます。

| イベント | 意味 |
|---|---|
| `HCI_IO_Capability_Request` | こちらの入出力の能力を教えて |
| `HCI_User_Confirmation_Request` | この6桁で正しいか、ユーザーに聞いて |
| `HCI_Link_Key_Notification` | できあがったリンクキーを保存して |

最後のイベントで分かるように、**リンクキーはホストへ渡されます**。保存場所が OS やホストの側にあるからです。そのため、HCI のログを取っている環境では、鍵もログに残ることがあります。

## 15.5 第3世代：Secure Connections

Core 4.1 の **Secure Connections** は、残っていた古い部分を置き換えました。

- 楕円曲線を P-192 から **P-256** に強化
- 認証を SAFER+ から **HMAC-SHA-256** に
- 暗号化を E0 から **AES-CCM** に。パケットに 32 ビットの MIC（[第7章](./ch07)）が付き、改ざんを検出できるようになった

AES-CCM を使う接続では、MIC つきのパケットが長いあいだ届かないと異常とみなす、**認証ペイロードタイムアウト**という監視も働きます。

SCO のパケットは E0 にしか対応していないので、AES-CCM の接続では使えません。通話には eSCO を使います（[第11章](./ch11)）。

### Secure Connections Only モード

互換性より安全性を優先する機器のために、**Secure Connections Only モード**があります。FIPS 承認のアルゴリズムだけを使い、古い方式しか話せない相手とは接続しません。機器がこのモードになると、BR/EDR と LE の両方に適用されます。

Secure Connections の鍵は次の点でも新しくなっています。機器が両方の方式に対応していれば、BR/EDR のリンクキーから LE の LTK を、逆に LTK からリンクキーを作ることができます。これを **Cross-Transport Key Derivation（CTKD）** と呼びます。ユーザーは1回ペアリングするだけで、Classic と LE の両方が使えるようになります。そのための L2CAP のチャネルとして、CID `0x0007` が予約されています。

### 暗号化の鍵の長さ

Classic の暗号化の鍵の長さは交渉で決まります。現在の仕様では **7〜16 バイト**（56〜128 ビット）です。

::: extra コア仕様の外からの補足：KNOB と BIAS
以前の仕様では、鍵の長さの交渉に 1 バイトまで認められていて、しかも交渉の内容が保護されていませんでした。2019 年に公表された **KNOB 攻撃**（CVE-2019-9506）は、電波に割り込んで鍵を最短にさせ、総当たりするというものです。SIG はこれを受けて、最小の長さを 7 バイトとする方向に仕様を改めました。今の LMP の仕様でも、交渉に使う鍵の長さの上限と下限は、どちらも 7 バイト以上と定められています。

2020 年に公表された **BIAS 攻撃**（CVE-2020-10135）は、以前ボンディングした相手のふりをして認証を通り抜けるものです。古い方式の認証の不備や、古い方式への格下げを利用します。

これらは「古い互換の残りを攻撃者が利用する」典型的な例です。機器のファームウェアを更新できるものは、更新しておきましょう。
:::

## 15.7 サービスごとの要求

機器の接続全体ではなく、サービスごとに必要な強さを決められます。GAP の **セキュリティモード4** です。

| レベル | 要求 | 用途 |
|---|---|---|
| 4 | MITM の保護、暗号化、P-256 など強いアルゴリズム | 最も高い |
| 3 | MITM の保護、暗号化 | 高い |
| 2 | 認証、暗号化（MITM の保護は不要） | 中程度 |
| 1 | 暗号化する場合は認証。ユーザーの手間は最小限 | 低い |
| 0 | 何も要らない | SDP やシグナリングなど |

L2CAP でチャネルを開くとき（[第13章](./ch13)）、要求されたレベルに足りなければ、まず鍵の手続きを行います。足りない状態なら「security block」という結果を返して拒否します。

レベル 0 は SDP と L2CAP のシグナリングなどに限られます。これらは鍵を作る前から動く必要があるからです。

モード1〜3 は古い方式で、現在の機器はモード4を使います。

::: spec
- **ARCH §5.1〜5.3**：Classic のセキュリティの全体像、SSP の目標、4つの方式
- **ARCH §5.6**：BR/EDR と LE の間の鍵の変換
- **ARCH §5.4**：LE のセキュリティ。本書では第30章で扱う
- **SEC §2〜§6**：Legacy のアルゴリズムの内部（E0、E1、E21、E22、SAFER+）
- **SEC §7**：SSP の各段階の暗号学的な解析
- **LMP §4.2**：認証、ペアリング、暗号化の PDU のシーケンス
- **GAP §5**：セキュリティモードとセキュリティレベルの正確な定義
:::

## まとめ

- Classic のペアリングはコントローラのリンクマネージャが LMP で行う
- Legacy Pairing は PIN だけが秘密なので、録音からのオフライン総当たりに弱い
- SSP は ECDH で盗聴を防ぎ、4つの方式で MITM に対応する。方式は入出力の能力で決まる
- SSP の6桁の数字は鍵の材料ではないので、知られても鍵は計算できない
- Secure Connections は P-256、HMAC-SHA-256、AES-CCM に更新し、完全性の保護を加えた
- 鍵はリンクキーから接続ごとに作る。CTKD で LE と鍵を共有できる
- セキュリティモード4では、サービスごとに必要なレベルを指定する

## 確認問題

1. 4桁の PIN でペアリングしたやり取りを録音された場合、何が問題でしょうか。
2. スマホとヘッドホンのペアリングが Just Works になる理由を説明してください。また、この方式で防げるものと防げないものは何でしょうか。
3. Numeric Comparison の6桁の数字を横から覗かれました。通信は安全でしょうか。
4. 通話中の eSCO が AES-CCM で暗号化されている場合、なぜ SCO に切り替えられないのでしょうか。

::: details 答え
1. 秘密が PIN だけなので、録音したやり取りを手元で計算して総当たりできます。1万通りしかないので、短時間で鍵が分かります。
2. ヘッドホンに画面やキーボードがなく、数字を確かめる手段がないからです。盗聴は防げますが、中間者攻撃は防げません。
3. 安全です。6桁は鍵の材料ではなく計算の結果なので、これを見ても鍵は計算できません。
4. SCO のパケットは E0 にしか対応していないからです。AES-CCM の接続では SCO は使えません。
:::
