# 第25章 SCO と eSCO：声を運ぶ

::: goal
- 通話の音声に専用の運び方が必要な理由を説明できる
- HV1、HV2、HV3 の違いと、64 kb/s の出どころを計算で示せる
- eSCO の再送の窓のしくみを説明できる
- 音楽が ACL で、通話が eSCO で運ばれる理由を説明できる
:::

Bluetooth は最初から、ヘッドセットで話すことを目標の1つにしていました。音声のために用意された専用の運び方が **SCO** と、その改良版の **eSCO** です。

## 25.1 予約席という発想

音声通話には、ファイル転送とは違う性質があります。

- データは一定の速さで生まれ続ける
- **遅れは困る**。会話がぎこちなくなる
- **多少の欠けは許せる**。人の耳は短い途切れに寛容

だから、ACL のように「成功するまで再送」する必要はありません。代わりに、決まった時間に必ず通信できることが大事です。

そこで SCO は、ピコネットの**スロットを定期的に予約**します。Central と相手の Peripheral は、予約したスロットで必ず通信します。仕様はこれを**回線交換**に近いと説明しています。電話回線のように、通話の間は決まった容量を確保し続けるわけです。

## 25.2 SCO：64 kb/s の予約席

SCO が運ぶのは **64 kb/s** の流れです。この数字は電話に由来します。

<div class="formula">8000 回／秒 × 8 ビット ＝ 64 kb/s</div>

1秒に8000回、音の大きさを8ビットで記録すると 64 kb/s になります。これが電話の音質です。人の声の主な成分である 4 kHz くらいまでの音を表せます（サンプリングの説明は[第9章](./ch09)）。

SCO のパケットには、誤り訂正の強さが違う3種類があります。

| 種類 | 音声のデータ | FEC | 予約の間隔 TSCO | 1パケットの音の長さ |
|---|---:|---|---:|---:|
| HV1 | 10 バイト | 1/3 | 2 スロット | 1.25 ms |
| HV2 | 20 バイト | 2/3 | 4 スロット | 2.5 ms |
| HV3 | 30 バイト | なし | 6 スロット | 3.75 ms |

HV は High-quality Voice の略です。名前の数字はスロット数ではないので注意してください。どれも1スロットのパケットです。

計算してみると、どれも 64 kb/s になっています。

<div class="formula">HV3：30 バイト × 8 ÷ (6 × 625 µs) ＝ 240 ビット ÷ 3.75 ms ＝ 64 kb/s</div>

ここにトレードオフがあります。HV1 は誤りに強いものの、**すべてのスロットを占領します**。データ通信も、別の機器との通信もできなくなります。HV3 は3分の2のスロットを空けておけますが、FEC がないので電波の誤りがそのまま音の雑音になります。

SCO のパケットには CRC もなく、再送もありません。受け取ったものをそのまま音にします。

予約したスロットでも、例外的により優先度の高い通信に譲ることがあります。LMP の制御メッセージを届ける必要があるときなどです。

## 25.3 eSCO：少しだけ再送する

**eSCO**（extended SCO）は Core 1.2 で追加されました。SCO の弱点は、誤りに対して打つ手がないことでした。eSCO は「遅れすぎない範囲で少しだけ再送する」という折衷案です。

<figcaption>図25-2 eSCO の時間割。予約のスロットで失敗したら、直後の再送の窓で送り直す。成功すれば窓のスロットは他の通信に使える</figcaption>
</figure>

| 特徴 | SCO | eSCO |
|---|---|---|
| 再送 | なし | 窓の中で限られた回数 |
| 誤りの検出 | なし | CRC あり |
| 速さ | 64 kb/s 固定 | 選べる |
| 向き | 対称 | 非対称も可 |
| EDR | 使えない | 使える |
| LT_ADDR | デフォルト ACL と同じ | 専用のものを割り当てる |
| 暗号化 | E0 のみ | E0 または AES-CCM |

eSCO のパケットには、EV で始まる名前がついています。

| 種類 | データの最大（バイト） | FEC | スロット | 最大の速さ（kb/s） |
|---|---:|---|---:|---:|
| EV3 | 30 | なし | 1 | 96 |
| EV4 | 120 | 2/3 | 3 | 192 |
| EV5 | 180 | なし | 3 | 288 |
| 2-EV3 | 60 | なし | 1 | 192 |
| 2-EV5 | 360 | なし | 3 | 576 |
| 3-EV3 | 90 | なし | 1 | 288 |
| 3-EV5 | 540 | なし | 3 | 864 |

最後の列は仕様の表（BB §6.7）に載っている上限です。実際の音声ではもっと余裕を持たせます。

eSCO は再送の窓を使うので、再送が必要なければそのスロットは他に回せます。つまり、再送のために確保する容量が無駄になりにくいのです。

eSCO の面白い点をもう1つ。受信側は CRC が合わないパケットでも、受け取ったことにして上へ渡してよいことになっています。音声では、全部捨てるより多少壊れていても使うほうがよい場合があるからです。データが壊れていたことをホストに知らせるしくみも用意されています。

::: tip AES-CCM と SCO
Secure Connections の AES-CCM で暗号化しているときは、SCO のパケットは送れません。SCO は古い E0 暗号にしか対応していないからです。そのため新しい機器の通話には eSCO が使われます（[第29章](./ch29)）。
:::

::: extra コア仕様の外からの補足：広帯域の通話
電話の音質（8 kHz サンプリング）では、「さ」と「ふ」のような高い音の成分が失われて聞き取りにくくなります。ハンズフリーのプロファイル HFP は、v1.6 で広帯域通話（mSBC コーデック、16 kHz サンプリング）を追加しました。

HFP の設定 T2 は、2-EV3 で片方向 8000 バイト/秒と定められています。これは 7.5 ms で 60 バイトにあたり、コーデックが 7.5 ms ごとに作るフレーム（同期ヘッダを含む）の大きさと一致します。1フレームを 1 パケットで送ると、次の計算になります。

<div class="formula">60 バイト × 8 ÷ (12 × 625 µs) ＝ 480 ビット ÷ 7.5 ms ＝ 64 kb/s</div>

さらに v1.9 では、LE Audio と同じ LC3 コーデックによる超広帯域の通話も加わりました（[第28章](./ch28)）。
:::

## 25.4 音の符号化

SCO で運ぶ 64 kb/s の中身として、Core 仕様は次の方式を定めています。

| 方式 | 考え方 |
|---|---|
| log PCM（A-law、µ-law） | 音の大きさを対数のものさしで 8 ビットに記録する。電話網で標準的に使われてきた方式 |
| CVSD | 値そのものでなく「前より上がったか下がったか」を 1 ビットで記録する。傾きの大きさは適応的に変える |

CVSD は 1 秒に 64000 回、1 ビットずつ記録するので 64 kb/s です。値の変化しか記録しないので、1 ビットが壊れても影響は小さく、すぐに元の波形に戻っていきます。雑音の多い無線にはこの頑丈さが向いています。

::: bio
活動電位の頻度による符号化を思い出してください。神経は振幅ではなく発火の頻度で強さを伝えます。CVSD も振幅そのものではなく、ビット列の「上下の傾向」で波形を表します。1回のパルスの欠落が致命的にならない点も少し似ています。
:::

## 25.5 音楽はなぜ eSCO ではないのか

通話が eSCO なら、音楽もそうすればよさそうです。でも音楽は ACL で運ばれます。理由を整理します。

| | 通話 | 音楽 |
|---|---|---|
| 向き | 双方向 | ほぼ片方向 |
| 許せる遅れ | 小さい（会話のため） | やや大きい（音声と映像が合えばよい） |
| データのレート | 一定 | 圧縮によって変わる場合がある |
| 必要な速さ | 64 kb/s ほど | 数百 kb/s |
| 再送 | ほとんどしない | 期限内なら何度でも |
| フレーム | なし | あり |

eSCO は固定の大きさと周期なので、レートが変わるデータに向きません（[第23章](./ch23)）。また音楽はバッファを持てるので、期限つきの ACL で何度も再送するほうが品質を保てます。

通話が入ると音楽が止まり、音質ががらりと変わることがあります。A2DP と HFP という別のプロファイルに切り替わるからです（[第28章](./ch28)）。

## 25.6 CPB：もう1つの定期便

Core 4.1 で追加された **CPB**（Connectionless Peripheral Broadcast）は、Central から**台数無制限**の受信機へ定期的にデータを放送するしくみです。

- Central は決まった間隔でパケットを流す。受信の確認はない
- 受信機は接続の手続きをしなくても受け取れる
- 代わりに、受信機はまず**同期トレイン**を聞いて、時間割と周波数の情報を手に入れる

## まとめ

- 音声は遅れに弱く、多少の欠けに強いので、スロットを予約する SCO と eSCO で運ぶ
- 64 kb/s は電話の 8000 回／秒 × 8 ビットに由来する
- HV1〜HV3 は FEC の強さとスロットの消費のトレードオフである
- eSCO は再送の窓と CRC を持ち、EDR も使える
- AES-CCM で暗号化すると SCO は使えない
- 音楽はレートが変わり、バッファも持てるので、期限つきの ACL で運ぶ
- CPB は同期トレインで準備して受信する、接続なしの定期放送である

## 確認問題

1. HV2 の 20 バイトが 64 kb/s になることを計算で確かめてください。
2. 通話中に HV1 を使っていると、ファイル転送が止まってしまいます。HV3 なら止まりません。なぜでしょうか。
3. eSCO で再送の窓が使われなかったスロットは、どうなるでしょうか。
4. 音楽を運ぶ A2DP が eSCO を使わないのはなぜでしょうか。理由を2つ挙げてください。

::: details 答え
1. 20 × 8 = 160 ビットを、4 スロット（2.5 ms）ごとに送ります。160 ÷ 2.5 ms = 64 kb/s です。
2. HV1 はすべてのスロットを使いますが、HV3 は 6 スロット中 2 スロットしか使わないので、残りの 4 スロットを ACL に使えるからです。
3. ACL など、ほかの通信に使えます。
4. たとえば次の点です。音楽にはフレームがあり、圧縮によってレートが変わる場合があること。バッファを持てるので遅れが許され、期限内に何度も再送できる ACL のほうが品質を保てること。ほぼ片方向の通信なので、対称な予約がもったいないこと。
:::
