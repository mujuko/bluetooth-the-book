# 第23章 定期アドバタイズと PAwR

::: goal
- 定期アドバタイズがスキャン側の電力を減らす理由を説明できる
- 同期情報の入手方法を2つ挙げられる（スキャンと PAST）
- PAwR のイベント、サブイベント、応答スロットの関係を図で説明できる
:::

第21章のアドバタイズは、受信する側に負担をかける方式でした。送信のタイミングがランダムにばらつくので、受信側はいつ来るか分からないパケットをずっと待たなければなりません。この章では、時間割を公開することでこの問題を解決する2つの方式を学びます。

## 23.1 定期アドバタイズ：時間割つきの放送

**定期アドバタイズ**（論理トランスポート名は PADVB）は、ランダムな遅れを入れず、決まった間隔でパケットを送ります。そして、その時間割を受信側に教えます。受信側は時間割どおりに起きて聞き、それ以外は眠っていられます。

Classic にも、同期トレインで時間割を教えてから決まった間隔で放送する CPB がありました（[第11章](./ch11)）。定期アドバタイズは、それに近い位置づけです。

::: analogy 時刻表のあるバス
時刻表のないバス停では、ずっと立って待つしかありません。時刻表があれば、到着の少し前にバス停に行けば十分です。
:::

::: bio
受信機が送信機のリズムに自分の活動を合わせる様子は、生物が光などの外部の信号に概日リズムを同調させる現象（エントレインメント）を思わせます。同調してしまえば、毎回信号を探し回らなくても、予定の時刻に体の準備が整います。
:::

時間割はどうやって伝えるのでしょうか。ここで第21章の拡張アドバタイズが生きてきます。

1. いつものように、プライマリチャネルに見出し `ADV_EXT_IND` を送る
2. 見出しが指す本文 `AUX_ADV_IND` の中に **SyncInfo** という欄があり、間隔、次回までの時間、チャネルの情報が書いてある
3. 受信側はそれに従って、定期パケット `AUX_SYNC_IND` を聞く

この後、受信側はプライマリチャネルをスキャンする必要がありません。一度時間割を知れば、次からは決まった時刻に決まったチャネルを聞くだけです。

定期パケットの連なりを**定期アドバタイズトレイン**といいます。各回の中身は変えられます。データが長ければ、`AUX_CHAIN_IND` で続きをつなぎます。定期アドバタイズに、スキャン要求や接続の申し込みで応えることはできません。

## 23.2 PAST：同期情報を教えてもらう

時間割を知るための最初のスキャンは、小さな機器にとっては電力を食う仕事です。そこで別の方法が用意されています。電力に余裕のある機器が代わりにスキャンして同期情報を手に入れ、それを接続経由で教えてあげるのです。これを **PAST**（Periodic Advertising Sync Transfer）といいます。

たとえば補聴器のためにスマホが放送を探し、見つけたら「このタイミングで聞いて」と LE-ACL で伝える、という使い方です。ここでも「電力に余裕のある機器が手間を引き受ける」という設計が見られます。

## 23.3 PAwR：返事ができる放送

定期アドバタイズは一方向でした。Core 5.4 で登場した **PAwR**（Periodic Advertising with Responses）は、そこに返事の機会を加えたものです。接続なしで双方向に通信できる、ちょっと変わった方式です。

代表的な応用が、スーパーの**電子棚札**です。店舗には数千枚の値札があり、すべてコイン電池で動きます。

- 接続を維持するには数が多すぎる
- 値札ごとに違う内容（値段）を送りたい
- 表示を更新したという確認がほしい
- ふだんはほとんど通信がない

PAwR はこれを次のように実現します。時間割を**イベント**と**サブイベント**に分け、値札（Observer）のグループごとに、聞くべきサブイベントを割り当てるのです。

<figcaption>図23-2 PAwR の時間割。イベントはサブイベントに分かれ（1イベントに最大128個）、各サブイベントの後半は受信側の返事の枠（応答スロット）になっている</figcaption>
</figure>

動きを順に見ましょう。

1. 放送側は、サブイベントの先頭で1パケットを送る。そのグループ向けのデータである
2. そのサブイベントに割り当てられた値札だけが起きて、聞く。ほかの値札は眠っている
3. 少し待った後に応答スロットが並ぶ。値札は自分に割り当てられた枠で返事を送る
4. 返事は同じチャネルで送る。チャネルはサブイベントごとに変わる

値札は自分の出番の一瞬だけ起きればよいので、電池が非常に長くもちます。

さらに放送側は、サブイベントの枠を使って特定の値札に接続を申し込むこともできます（`AUX_CONNECT_REQ`）。大きな画像データを送るときなどは、普通の接続に切り替えられるわけです。

## 23.4 定期アドバタイズと PAwR の比較

| | 定期アドバタイズ（PADVB） | PAwR |
|---|---|---|
| 接続 | なし | なし |
| 方向 | 放送側から受信側へのみ | 双方向 |
| 時間の単位 | イベント | イベントとサブイベント |
| データの内容 | 全員に同じ。変化は比較的少ない | 受信者ごとに変えられる。頻繁な変更が前提 |
| 接続の申し込み | できない | できる |
| PAST | 任意 | 必須 |

## 23.5 誰が割り当てを決めるのか

受信側が PAwR に参加するには、3段階の情報が必要です。

1. イベントの間隔とタイミング
2. サブイベントと応答スロットの構造
3. **自分がどのサブイベントを聞き、どの枠で返事をするか**

1と2は規格の手順（スキャンまたは PAST）で手に入ります。しかし3は、規格の下の層では決まりません。アプリの層、たとえば電子棚札（ESL）のプロファイルが決めることです。「どの値札をどのグループにするか」は、応用によって違うからです。

このように、「手段は下の層が提供し、使い方は上の層が決める」という分担は、スタック全体によく見られる考え方です。

## まとめ

- 定期アドバタイズは、決まった時間割で送り、その時間割を公開する。受信側は必要なときだけ起きればよい
- 時間割は `AUX_ADV_IND` の SyncInfo から得るか、PAST で他の機器に教えてもらう
- PAwR は定期アドバタイズに返事の枠を加えたもので、多数の機器を個別に低電力で扱える
- サブイベントや枠の割り当ては、アプリの層が決める

## 確認問題

1. 定期アドバタイズにランダムな遅れがないのは、なぜ許されるのでしょうか。通常のアドバタイズでは衝突を避けるために必要だったはずです。
2. PAST を使うメリットを、電力の観点で説明してください。
3. 店舗の案内を全員のスマホに一斉に配るだけなら、PAwR と定期アドバタイズのどちらが向いていますか。

::: details 答え
1. 本文は汎用チャネルを使い、チャネルもイベントごとに変わるので、同じ機器と衝突し続ける心配が小さいからです。加えて、受信側が予定どおり受信できることこそ、この方式の目的です。
2. 時間のかかるスキャンを、小さな機器が自分でせずに済むからです。電力に余裕のある機器が代わりに行います。
3. 定期アドバタイズです。全員に同じデータを配るだけで、返事はいりません。
:::
