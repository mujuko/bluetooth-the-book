# 第28章 GATT：データに意味を与える

::: goal
- サービス、キャラクタリスティック、ディスクリプタの関係を説明できる
- GATT の構造がアトリビュートテーブルでどう表されるかを説明できる
- 通知を受けるのに CCCD への書き込みが必要な理由を説明できる
- 16ビットと128ビットの UUID を使い分けられる
- 心拍データのバイト列を読み解ける
:::

第27章の ATT は、値の意味を問わないただの表でした。その表に構造を与えるのが **GATT**（Generic Attribute Profile）です。アプリ開発者がいちばん多く接する層で、「BLE の開発」といえば、たいていはこの層の話になります。

## 28.1 3階層のデータ構造

GATT はデータを3つの階層で整理します。

**サービス**は機能のまとまりです。「心拍」「電池残量」のように、機器の能力のひとつの側面に対応します。

**キャラクタリスティック**は個々のデータ項目です。「心拍数の測定値」「センサを付ける体の位置」といったものです。値と、どう扱えるかを示す**プロパティ**（読める、書ける、通知できる、など）を持ちます。

**ディスクリプタ**はキャラクタリスティックの付帯情報です。説明の文字列や、後で見る通知の設定など、0個以上つきます。

## 28.2 構造は「表」でどう表現されるか

GATT の階層は、ATT の平らな表の上に、決まった書き方で表現されます。図28-1 の心拍サービスの部分は、たとえば次のようになります。

| ハンドル | 種類（UUID） | 値 | 説明 |
|---|---|---|---|
| `0x0010` | `0x2800` サービス宣言 | `0x180D` | ここから心拍サービス |
| `0x0011` | `0x2803` キャラクタリスティック宣言 | 通知可／`0x0012`／`0x2A37` | 次の行が心拍数の測定値で、通知できる |
| `0x0012` | `0x2A37` 測定値 | `06 48` | データの本体 |
| `0x0013` | `0x2902` CCCD | `00 00` | 通知の設定（今はオフ） |
| `0x0014` | `0x2803` キャラクタリスティック宣言 | 読取可／`0x0015`／`0x2A38` | 次の行が体の位置で、読める |
| `0x0015` | `0x2A38` 体の位置 | `01` | データの本体（1 は胸） |

ポイントは次のとおりです。

- 1つのサービスは、連続したハンドルの範囲を占める
- サービスやキャラクタリスティックの始まりは「宣言」の行で示す
- 1つのキャラクタリスティックは、宣言の行と値の行の2行以上を使う

クライアントはこの構造をたどることで、初めて会った機器の能力を自動で知ることができます。これを**サービスディスカバリ**といいます。

Classic の SDP（[第13章](./ch13)）は「どのプロトコルで、どこへつなげばよいか」を教えるだけで、データのやり取りは別のプロトコルに任せていました。GATT は、データそのものの場所と意味まで教え、同じ ATT で読み書きを続けます。

::: deep プロパティとパーミッション
似た言葉なので混乱しやすいところです。**プロパティ**は宣言の行に書かれ、「このデータで何ができるか」をクライアントに知らせる情報です。**パーミッション**はサーバの内部にある規則で、「暗号化された接続でなければ読ませない」のような条件をサーバが実際に強制します。プロパティが「読める」でも、パーミッションの条件を満たさなければエラーが返ります（第30章）。
:::

## 28.3 CCCD：通知を購読する

心拍計は勝手に通知を送り始めてよいわけではありません。クライアントが必要としていないのに電波を出すのは無駄だからです。そこで、「通知してほしい」という意思表示を、ディスクリプタへの書き込みで行います。

このディスクリプタが **CCCD**（Client Characteristic Configuration Descriptor）です。

| 書き込む値 | 意味 |
|---|---|
| `00 00` | 止める |
| `01 00` | 通知（notification）を有効にする |
| `02 00` | インディケーションを有効にする |

通知かインディケーションを持つキャラクタリスティックには、必ず CCCD がなければなりません。

## 28.4 バイト列を読み解く

通知で届く `06 48` は何を意味するのでしょうか。形式を定めているのは Heart Rate Service の仕様です。

| バイト | 値 | 意味 |
|---|---|---|
| 1バイト目 | `0x06`（2進数で `00000110`） | フラグ。最下位ビットが0なので、心拍数は1バイトの形式。次の2ビットは皮膚との接触の状態 |
| 2バイト目 | `0x48` | 心拍数 72（4×16 + 8） |

フラグの最下位ビットが1なら心拍数は2バイトで表されます。普通の人の心拍数なら1バイトで足りますが、規格は余裕を持たせているわけです。

ここに ATT と GATT の分担がよく表れています。ATT はただ2バイトを運ぶだけで、GATT は「ここがキャラクタリスティックの値だ」と決め、サービス仕様が「このバイトは心拍数だ」と決めます。

なお、Bluetooth の複数バイトの数は、原則として**小さい桁のバイトが先**（リトルエンディアン）です。CCCD の `0x0001` を `01 00` と書いたのはこのためです。

## 28.5 同じ型、違う意味

同じ UUID のキャラクタリスティックが、別のサービスに入っていることがあります。たとえば**警告レベル**（Alert Level、`0x2A06`）は、Link Loss Service と Immediate Alert Service の両方に出てきます。

- Immediate Alert Service の中では「今すぐ、このレベルで鳴らせ」という命令
- Link Loss Service の中では「接続が切れたら、このレベルで鳴らせ」という設定

サービスが文脈を与えて、同じデータ型に違う役割を持たせているのです。

::: bio
同じ遺伝子産物が、組織や経路によって異なる役割を果たすようなものです（ムーンライティングタンパク質など）。分子の種類は同じでも、文脈で働きが変わります。
:::

## 28.6 UUID：SIG の番号と独自の番号

種類を表す UUID には2つの形があります。

**16ビット UUID**は Bluetooth SIG が割り当てる短い番号で、`0x180D` のような形です。Assigned Numbers に載っています。

なぜ短い番号を用意したのでしょうか。128ビットの UUID は16バイトもあります。レガシーのアドバタイズのデータは最大31バイトしかないので（第21章）、2バイトで書ければ、残りを名前などに使えます。小さなパケットで動く LE では、この14バイトの差が大きいのです。

**128ビット UUID**は、誰でも作れる長い番号です。乱数で作るので、衝突の心配はほぼありません。メーカーが独自のサービスを定義するときに使います。

```
16ビット UUID 0x180D は、実は次の128ビットの省略形
0000180D-0000-1000-8000-00805F9B34FB
```

この範囲（`0000xxxx-0000-1000-8000-00805F9B34FB`）は SIG の管理下にあるので、自分の UUID として勝手に使ってはいけません。独自の UUID は、ツール（Linux や macOS なら `uuidgen` コマンド）で生成します。

1つの GATT サーバの中で、標準のサービスと独自のサービスを混在させてかまいません。実際、多くの製品は電池のような標準サービスと、製品固有の独自サービスを併せ持っています。

## 28.7 必須のサービスと手続き

GATT サーバには、決まった役目を持つサービスが2つあります。

- **Generic Access Service**（`0x1800`）：機器の名前（Device Name）や外観。すべての GATT サーバに必須
- **Generic Attribute Service**（`0x1801`）：表の変更の通知（Service Changed）など。表の中身が後から変わる機器は、ここに Service Changed を置かなければならない

GATT は、クライアントの操作を「手続き」として定義し、どの ATT の PDU に対応するかを定めています。プラットフォームの API もだいたいこれに対応しています。

| GATT の手続き | 使う ATT の PDU |
|---|---|
| サービスの検索 | `ATT_READ_BY_GROUP_TYPE_REQ` / `RSP` |
| キャラクタリスティックの検索 | `ATT_READ_BY_TYPE_REQ` / `RSP` |
| ディスクリプタの検索 | `ATT_FIND_INFORMATION_REQ` / `RSP` |
| 読み出し | `ATT_READ_REQ` / `RSP` |
| 書き込み（応答あり） | `ATT_WRITE_REQ` / `RSP` |
| 書き込み（応答なし） | `ATT_WRITE_CMD` |
| 通知 | `ATT_HANDLE_VALUE_NTF` |
| インディケーション | `ATT_HANDLE_VALUE_IND` / `CFM` |

## まとめ

- GATT はサービス、キャラクタリスティック、ディスクリプタの3階層でデータを整理する
- 階層は ATT の表の上に、宣言の行を使って表現される
- 通知を受けるには、CCCD に `01 00` を書き込んで購読する
- 値の意味はサービス仕様が決める。多バイトの値はリトルエンディアン
- 16ビット UUID は SIG が割り当て、128ビット UUID は誰でも作れる

## 確認問題

1. 心拍データ `06 3C` は心拍数いくつを表すでしょうか。
2. 心拍計に接続しただけでは通知が来ません。何が足りないのでしょうか。
3. 16ビット UUID `0x180F` を128ビットで書いてください。
4. 自社製品の独自サービスに `0000AAAA-0000-1000-8000-00805F9B34FB` を使ってよいでしょうか。

::: details 答え
1. `0x3C` は 3×16 + 12 = 60 です。心拍数 60 を表します。
2. CCCD への書き込み（`01 00`）です。
3. `0000180F-0000-1000-8000-00805F9B34FB` です。
4. いけません。その範囲は SIG の管理下にあります。乱数で作った128ビットの UUID を使うか、16ビットの UUID を SIG から購入します。
:::
