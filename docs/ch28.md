# 第28章 プロファイル

::: goal
- プロファイルが何を定めるものかを説明できる
- GAP を土台としたプロファイルの階層を説明できる
- A2DP、HFP、SPP、HID が、それぞれどのプロトコルの上にあるかを言える
- 音楽と通話で別のプロファイルを使う理由を説明できる
:::

コア仕様が用意したのは、運び道（ACL、eSCO、L2CAP）と、検索の手段（SDP）までです。その上で「音楽を聴く」「電話に出る」を実現するのが**プロファイル**です。この章の後半は Core 仕様の外の話が中心です。

## 28.1 プロファイルとは

2台の機器が L2CAP でつながっても、同じ言葉で話さなければ音は鳴りません。音の形式は？再生の開始の合図は？プロファイルは、ある用途のために**スタックの全体をどう使うかを決めた取り決め**です。

Architecture 編の説明を整理すると、プロファイルは次のものを定めます。

- 各層で必須の機能（PHY から L2CAP、さらに上のプロトコルまで）
- 層と層の間の縦の関係、2台の同じ層どうしの横の関係
- アプリの動作とデータの形式
- サービス検索の要件（SDP に何を書くか）

2台の機器が同じプロファイルの要件を満たしていれば、メーカーが違っても動きます。

::: analogy
L2CAP までは「道路と配送の決まり」です。プロファイルは「レストランのデリバリーでは、この順番で注文し、この容器で運び、玄関でこう受け渡す」という**業界の取り決め**です。お店（メーカー）が違っても、同じ取り決めなら客（別のメーカーの機器）は困りません。
:::

## 28.3 主なプロファイル

::: extra コア仕様の外からの補足
ここからの内容は、Core 仕様の外の各プロファイルの仕様書に書かれています。本書の記述に関わる部分は、[付録D](./core-map#プロファイルの仕様書との照合)の版と照合しました。全体の定義は各仕様書にあたってください。
:::

| プロファイル | 用途 | 主なプロトコル | サービスの UUID の例 |
|---|---|---|---|
| A2DP | 音楽の配信 | AVDTP | `0x110A`（Source）, `0x110B`（Sink） |
| AVRCP | 再生の操作、音量など | AVCTP | `0x110C`（Target）, `0x110E`（Controller） |
| HFP | ハンズフリー通話 | RFCOMM、eSCO または SCO | `0x111E`（HF）, `0x111F`（AG） |
| HSP | 簡易なヘッドセット | RFCOMM、SCO（eSCO も可） | `0x1108` |
| SPP | シリアルケーブルの代わり | RFCOMM | `0x1101` |
| HID | キーボード、マウス、ゲームパッド | HID プロトコル | `0x1124` |
| OPP | オブジェクトの送受信 | OBEX（L2CAP または RFCOMM の上） | `0x1105` |
| PBAP | 電話帳の読み出し | OBEX（同上） | `0x112F`（Server） |
| MAP | メッセージの閲覧と送信 | OBEX（同上） | `0x1132`（Server） |

### RFCOMM：線を作る

RFCOMM は、L2CAP の上に**シリアルポートのような通信路**を作るプロトコルです（PSM `0x0003`）。Bluetooth の出発点が「ケーブルの置き換え」だったことが、ここによく現れています。携帯電話の規格 ETSI TS 07.10 の一部を選び、Bluetooth 向けの変更を加えたもので、RS-232 の9本の信号線も再現できます。

サービスはサーバチャネル番号（1〜30）で区別します。番号は SDP で調べます（[第27章](./ch27)）。2台の間で同時に最大 60 本の接続を張れますが、実際に使える本数は実装によります。

アプリから見ると、ソケットを開いてバイト列を流すだけの単純な通路です。TCP に近い感覚で使えるので、開発ボードと PC の通信などで今も広く使われています。

### A2DP：音楽を流す

**A2DP**（Advanced Audio Distribution Profile）は、音楽を片方向に流すプロファイルです。送る側を **Source**（スマホ）、受ける側を **Sink**（ヘッドホン）と呼びます。**AVDTP** というプロトコルの上で動きます。AVDTP はインターネットの RTP を土台にしたプロトコルで、音楽を送るだけなら L2CAP のチャネルを2本使います。

| チャネル | 流れるもの |
|---|---|
| シグナリング | コーデックの交渉、開始、停止 |
| メディア | 音楽のデータそのもの |

どちらも PSM `0x0019` です。始めるまでの流れはおおむね次のとおりです。

手続きを始めた側は、相手の能力を見て設定を選びます。Source と Sink のどちらから始めてもかまいません。

A2DP の必須のコーデックは **SBC** です。Source は SBC のエンコーダを、Sink はデコーダを必ず持ちます。そのほかに任意のコーデックとして MPEG-1,2 Audio、AAC、ATRAC、MPEG-D USAC が定められていて、それ以外のものはベンダー固有のコーデックとして扱います。両者が同じものに対応していれば使えます。

**どれくらいの帯域を使うのか**、計算してみましょう。A2DP の仕様書が Source に推奨する SBC の高音質の設定は、44.1 kHz のジョイントステレオで 328 kb/s です。3-DH5（1021 バイト）で運ぶと、

<div class="formula">328,000 ビット/秒 ÷ (1021 × 8 ビット) ≒ 40 パケット/秒<br>40 × 6 スロット ＝ 240 スロット ＝ 1600 の 15%</div>

上の層のヘッダを無視すれば、電波の時間の15%ほどです。残りは再送や他の機器に使えます。これだけ余裕があるので、電波の状況が悪くても再送で乗り切れます。

### AVRCP：操作を送る

再生、一時停止、音量の操作は別のプロファイルの **AVRCP** が担当します。コマンドは **AVCTP**（PSM `0x0017`）で流れます。コマンドの体系は、IEEE 1394 の業界団体が定めた AV/C を取り入れたものです。A2DP がデータを、AVRCP が操作をと、役割を分けています。

コマンドを送る側を **Controller（CT）**、受ける側を **Target（TG）** と呼びます。ヘッドホンのボタンで再生を操作するときは、ヘッドホンが CT です。逆にスマホから絶対音量を設定するときは、音を出すヘッドホンが TG になります。1台が両方の役割を持つこともあるわけです。

### HFP：電話に出る

**HFP**（Hands-Free Profile）は通話のプロファイルです。役割は **AG**（Audio Gateway、スマホ）と **HF**（Hands-Free、ヘッドホンやカーナビ）です。

特徴は、**制御と声が別の道を通る**ことです。

| | 通り道 | 内容 |
|---|---|---|
| 制御 | RFCOMM の上の AT コマンド | 着信、応答、電話番号の通知など |
| 声 | eSCO または SCO | L2CAP を通らない |

AT コマンドは、電話回線のモデムの時代からある文字のコマンドです。HF は `AT+BRSF` で自分の機能を伝えて AG の機能を受け取り、`AT+BAC` で使えるコーデックを伝えます。AG は `RING` で着信を知らせ、`+BCS` で使うコーデックを伝えます。40年以上前に生まれた形式が、今のイヤホンの中で動いているのは楽しい話です。

通話の音質は、版を重ねて次のように拡張されてきました。

| コーデック | 呼び方 | 音の形式 | 運び道 | 位置づけ |
|---|---|---|---|---|
| CVSD | 狭帯域 | 電話の音質 | eSCO または SCO | 必須 |
| mSBC | 広帯域 | 16 kHz、モノラル | eSCO のみ | v1.6 で追加。広帯域に対応するなら必須 |
| LC3-SWB | 超広帯域 | 32 kHz、モノラル | eSCO のみ | v1.9 で追加。超広帯域に対応するなら必須 |

LC3 は LE Audio と同じコーデックです（[第9章](./ch09)）。使える eSCO の設定には名前がついていて、CVSD は S1〜S4、mSBC と LC3-SWB は T1（EV3）と T2（2-EV3）です。Secure Connections を使う接続では、S4 や T2 を使います。

### HID：入力機器

キーボード、マウス、ゲームパッドなどは **HID**（Human Interface Device）プロファイルを使います。USB の HID と同じ考え方のレポートを、L2CAP の2本のチャネルで運びます。

| PSM | チャネル | 用途 |
|---|---|---|
| `0x0011` | Control | 設定やレポートの要求など |
| `0x0013` | Interrupt | 要求なしで流すレポート（キー入力など）。確認の返事はない |

HID の機器はほとんどが電池で動くので、電力の管理は機器自身の責任とされています。仕様は Sniff サブレーティングの使用を勧めていて、短い間隔の Sniff を普段の状態にしてもかまいません（[第26章](./ch26)）。

## 28.4 同時に使う

実際のヘッドホンは A2DP、AVRCP、HFP を組み合わせて使います。次の流れは典型的な製品の例で、細かい動きは機器によって違います。

- 音楽を聴いているときは A2DP が流れ、AVRCP と HFP は待機している
- 着信があると、HFP の RFCOMM で知らせが来る
- 電話に出ると eSCO が立ち上がり、A2DP は一時停止する

通話中に音質ががらりと変わるのは、この切り替えのためです。音楽用の A2DP は片方向なので、マイクの音を送り返せません。マイクを使うには HFP の eSCO に切り替える必要があるのです。音質は通話用のコーデックの水準に下がります。

LE Audio では、音楽も通話も LC3 と CIS という同じしくみで運べます（[第9章](./ch09)）。

::: bio
プロファイルの階層は、代謝経路の共通の部分に似ています。解糖系のような共通の経路を土台にして、細胞ごとに必要な枝を足していく。すべてのプロファイルが GAP を土台にして、用途の枝を足していくのと同じです。
:::

::: spec
- **ARCH §6.1〜6.3**：プロファイル、GAP、階層の説明（本章の前半）
- **ARCH §6.4〜6.5**：GATT ベースのプロファイルの階層。本書では LE 編で扱った
- **GAP**：GAP の全要件
- Core 仕様の外：[Bluetooth SIG の仕様書の一覧](https://www.bluetooth.com/specifications/specs/)に、各プロファイルの仕様書がある
- **RFCOMM §2、§5**：TS 07.10 との関係、DLCI とサーバチャネルの割り当て、クレジット方式の流量調整
- **AVDTP §6、§7**：信号の手順、RTP に基づくメディアパケット、遅延の報告、リカバリの機能
- **GAVDP §3**：ストリームを開く手順。Sink から始める場合と Source から始める場合

- **HID §5.1.8**：Sniff のパラメータの決め方
- **GOEP §6**：OBEX over RFCOMM を使う古い版との互換の手順

## まとめ

- プロファイルは、ある用途のためのスタックの使い方の取り決めである
- GAP を土台に、汎用のプロファイル、アプリケーションプロファイルと積み重ねる
- Classic では、プロファイルごとに使うプロトコルが違う
- A2DP は AVDTP の上で音楽を流し、AVRCP は操作を、HFP は RFCOMM と eSCO で通話を担当する
- HFP では制御と声が別の道を通る
- 音楽と通話を切り替えると、プロファイルごと切り替わるので音質が変わる

## 確認問題

1. A2DP の SBC の 328 kb/s を 2-DH5（679 バイト）で運ぶと、1600 スロットの何パーセントを使うでしょうか。上の層のヘッダは無視します。
2. 通話の声はどの運び道を通るでしょうか。L2CAP を通るでしょうか。
3. ヘッドホンで音楽を聴きながら音声アシスタントを起動すると音質が変わります。なぜでしょうか。
4. スマホのアプリと開発ボードの間でバイト列を簡単に流したいとき、どのプロファイルが手軽でしょうか。

::: details 答え
1. 328,000 ÷ (679 × 8) ≒ 60.4 パケット/秒です。1パケットで6スロット使うので 362 スロット、1600 の約 23% です。
2. eSCO（または SCO）を通ります。L2CAP は通りません。
3. マイクの音を送り返すには HFP の eSCO が必要で、A2DP から切り替わるからです。
4. SPP です。RFCOMM の上で、ソケットのようにバイト列を流せます。
:::
