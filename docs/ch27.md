# 第27章 L2CAP と SDP

::: goal
- Classic の L2CAP で動的チャネルを開く手順を追える
- PSM と CID の違いを説明できる
- L2CAP のモードの違いを説明できる
- SDP のサービスレコードを読み、相手につなぐ方法を読み取れる
:::

いよいよホストの世界です。ACL-U という1本の道の上で、どうやって複数のアプリの通路を作り、相手がどんな機能を持っているかを調べるのかを見ていきます。

## 27.1 L2CAP の役割

L2CAP の基本は LE と同じです（[第12章](./ch12)）。仕事は、**振り分け**、**分割と組み立て**、そして必要に応じた**流量調整と誤り制御**です。

ただ、Classic と LE では普段の使い方が少し違います。

| | Classic | LE |
|---|---|---|
| 主に使うチャネル | 必要なときに開く**動的チャネル** | ATT の**固定チャネル** |
| MTU の既定値 | 672 バイト（最低 48 バイト） | 23 バイト（ATT） |
| 誤り制御 | ベースバンドの CRC を補うモードあり | CRC が長いので不要 |
| 接続のない通信 | あり（CID `0x0002`） | なし |

ACL-U の上で使う CID は次のとおりです。

| CID | 用途 |
|---|---|
| `0x0000` | 使わない |
| `0x0001` | L2CAP のシグナリング（チャネルの開閉など） |
| `0x0002` | 接続のない通信 |
| `0x0007` | BR/EDR Security Manager（[第29章](./ch29)） |
| `0x0040`〜 | 動的に割り当てる |

## 27.2 チャネルを開く

動的チャネルを開くときは、**PSM**（Protocol/Service Multiplexer）という番号で「どのサービスにつなぎたいか」を指定します。

- **PSM**：サービスの番号。**相手のサービスの窓口**を示す
- **CID**：できあがった通路の両端の番号。機器ごとに自由に割り当てる

TCP に例えると、PSM は接続先のポート番号（80番なら Web）、CID はソケットを識別するローカルな番号に近いでしょう。

両端の CID が違う値でよいことに注意してください。自分の CID は相手に宛先として教え、相手に送るときは相手の CID を付けます。

途中で相手が暗号化を要求することもあります。その場合は CONNECTION_RSP が「保留」となり、ペアリングや暗号化が終わってから成功の返事が来ます（[第29章](./ch29)）。

### PSM の番号

PSM には少し変わった規則があります。必ず**奇数**で、しかも上位のバイトの最下位ビットは 0 です。番号の長さを可変にするための工夫で、「最初の偶数のバイトが見つかったら、そこが PSM の終わり」と判定できます。

小さな番号は SIG が割り当て、大きな番号は動的に割り当てて SDP で相手に伝えます。

| PSM | プロトコル |
|---|---|
| `0x0001` | SDP |
| `0x0003` | RFCOMM |
| `0x000F` | BNEP |
| `0x0011` | HID の制御 |
| `0x0013` | HID の割り込み |
| `0x0017` | AVCTP |
| `0x0019` | AVDTP |
| `0x001F` | ATT |

## 27.3 モード：誤りと流量の制御

[第24章](./ch24)で、16 ビットの CRC では見逃しが問題になりうると述べました。L2CAP は、チャネルごとに次のモードから動作を選べます。設定のときに交渉します。

| モード | 分割 | 流量調整 | 再送 | 用途の例 |
|---|---|---|---|---|
| Basic | なし | なし | なし | 下の層に任せる標準の動作 |
| Enhanced Retransmission | あり | あり | **あり** | 確実に届けたいデータ |
| Streaming | あり | なし | なし（受信側で捨てる） | 期限のあるストリーム |
| Retransmission | あり | あり | あり | 古い方式。現在は上のモードを推奨 |
| Flow Control | あり | あり | なし | 古い方式 |

Enhanced Retransmission モードと Streaming モードは Core 3.0 で加わりました。L2CAP のフレームに 16 ビットの FCS（誤り検出の値）を付けられ、ベースバンドの再送をすり抜けた誤りや、フラッシュで欠けたデータを検出して回復できます。

::: se
ベースバンドの ARQ は Wi-Fi の MAC 層の再送のような「電波の区間の」対策で、L2CAP の Enhanced Retransmission は TCP の再送に近い「L2CAP の両端の間の」対策です。二重に見えますが、守っている範囲が違います。
:::

### L2CAP の中身を担当する部品

Architecture 編は、L2CAP の内部に次の2つの役割を挙げています。

- **チャネルマネージャ**：相手のチャネルマネージャと話してチャネルを作る。必要に応じて LM に頼み、論理リンクの品質を調整する
- **資源マネージャ**：どのチャネルのデータを先に下へ渡すかを決める。チップのバッファと HCI の帯域は有限なので、QoS を約束したチャネルが飢えないようにする

## 27.4 SDP：相手に何ができるかを尋ねる

ヘッドホンにつながっても、音楽を聴けるのか、通話ができるのかはまだ分かりません。それを調べるのが **SDP**（Service Discovery Protocol）です。SDP は L2CAP の PSM `0x0001` で動きます。

SDP の考え方は単純です。

- **サーバ**は、自分が提供するサービスのデータベースを持つ
- データベースの1項目が**サービスレコード**
- サービスレコードは**属性**（ID と値の組）の集まり
- **クライアント**は、UUID で検索して必要な属性を取り出す

たとえば、音楽を受けられるヘッドホンの場合のサービスレコードは次のようになります。

| 属性 | 値 | 意味 |
|---|---|---|
| ServiceClassIDList | `0x110B`（Audio Sink） | このサービスの種類 |
| ProtocolDescriptorList | L2CAP（PSM=`0x0019`）、AVDTP（版番号） | **どのプロトコルでどこへつなげばよいか** |
| BluetoothProfileDescriptorList | `0x110D`（A2DP、版番号） | 対応するプロファイルと版 |
| BrowseGroupList | `0x1002` | 一覧表示に出すかどうか |

一番大事なのは **ProtocolDescriptorList** です。ここに「このサービスは L2CAP の PSM `0x0019` の上の AVDTP で使える」と書いてあります。つまり、SDP の答えをそのまま使って接続できます。

別の例も見てみましょう。シリアルポート（SPP）のサービスなら、ProtocolDescriptorList は「L2CAP の上の RFCOMM、サーバチャネル 3」のようになります。RFCOMM の PSM は固定ですが、その上のチャネル番号はサービスごとに違うので、SDP で調べる必要があります。

SDP の PDU は3組しかありません。

| PDU | 働き |
|---|---|
| `SDP_SERVICE_SEARCH_REQ` / `RSP` | UUID で検索して、レコードの番号の一覧を得る |
| `SDP_SERVICE_ATTR_REQ` / `RSP` | レコードの番号を指定して、属性を得る |
| `SDP_SERVICE_SEARCH_ATTR_REQ` / `RSP` | 上の2つを一度に行う |

### UUID

UUID の考え方は LE と同じです（[第14章](./ch14)）。16 ビットの短い値は、基準の UUID に埋め込んだものの略記で、基準の値も共通です。

<div class="formula">0x110B → 0000<b>110B</b>-0000-1000-8000-00805F9B34FB</div>

ただし、Classic のプロファイルの UUID は `0x11xx` の範囲にあり、プロトコルの UUID は `0x0100`（L2CAP）や `0x0003`（RFCOMM）のように別の範囲にあります。

### SDP と GATT の違い

| | SDP | GATT |
|---|---|---|
| 分かるもの | **どう接続すればよいか** | **データそのものの場所と意味** |
| その後 | 別のプロトコルに移る | 同じ ATT で読み書きを続ける |
| 接続 | 使うときだけ開く | 接続中ずっと使う |

SDP は電話帳のようなもので、番号を調べたら一度閉じて、その番号に電話をかけます。GATT はメニューの並んだ窓口で、その場で注文までできます。

SDP は暗号化なしでも使えます。セキュリティレベル 0 で許されているのは、シグナリングのチャネルと SDP などに限られます（[第29章](./ch29)）。つながる前に相手の機能が分からないと、何のために鍵を作るのかも決められないからです。

::: tip SDP が定めないこと
SDP は「サービスがある」ことと「どこにあるか」を教えてくれますが、使い方は定めていません。使い方はプロファイルの仕様に書いてあります（[第28章](./ch28)）。
:::

::: spec
- **ARCH §3.1.1**、**§3.6**：フレームつきのデータと L2CAP チャネルの説明
- **ARCH §2.1.1**：ホスト側の各ブロックの説明
- **L2CAP §3**：フレームの形式（B-frame、I-frame、S-frame、G-frame）
- **L2CAP §4、§5**：シグナリングの全コマンドと設定オプション（Flush Timeout、QoS、再送、FCS）
- **L2CAP §8**：Enhanced Retransmission モードの状態遷移
- **SDP §2**：サービスブラウジング（グループの階層をたどる）
- **SDP §3**：データ要素の型と長さの符号化
- **SDP §4、§5**：PDU の形式、続きの受け取り（ContinuationState）、universal attribute の一覧
:::

## まとめ

- Classic の L2CAP は、必要なときに動的チャネルを開いて使うのが基本である
- PSM はサービスの窓口、CID は通路の両端の番号である
- チャネルは接続、両方向の設定の順に開く
- モードを選ぶことで、L2CAP の段階でも再送や流量調整ができる
- SDP は L2CAP の上で動き、ProtocolDescriptorList で「どう接続すればよいか」を教えてくれる
- SDP は電話帳、GATT は窓口のようなものである

## 確認問題

1. PSM と CID のうち、機器によって値が変わるものはどちらでしょうか。
2. L2CAP の MTU を 1000 と伝えた機器は、何を約束したのでしょうか。
3. RFCOMM を使うサービスを見つけたのに、まだ SDP が必要なのはなぜでしょうか。
4. 相手のヘッドホンが A2DP に対応しているか調べたいとき、SDP でどの UUID を探しますか。

::: details 答え
1. CID です（動的チャネルの場合）。SIG が割り当てた PSM は共通です。
2. 「自分はこのチャネルで 1000 バイトまで受け取れる」という約束です。送れる大きさではなく受けられる大きさを伝えます。
3. RFCOMM の PSM は固定ですが、その上のサーバチャネルの番号はサービスごとに違うので、SDP で調べる必要があるからです。
4. 音楽を受ける側のサービスを探すので Audio Sink の `0x110B` です。A2DP のプロファイルを表す `0x110D` は BluetoothProfileDescriptorList に入っています。
:::
