# 第13章 ATT：相手の表を読み書きする

::: goal
- アトリビュートの4つの要素を説明できる
- 4種類のやり取りのパターンを、向きと応答の有無で区別できる
- トランザクションの制約と、EATT が解決することを説明できる
:::

いよいよデータの中身に近づいてきました。**ATT**（Attribute Protocol）は、接続した相手の持つ「表」を読み書きするためのプロトコルです。

## 13.1 クライアントとサーバ

ATT の世界の登場人物は2人です。

- **サーバ**：データの表を持っている
- **クライアント**：その表を読み書きする

心拍計の場合、心拍計がサーバで、スマホがクライアントです。

::: warning よくある混同
**クライアントとサーバは、セントラルとペリフェラルとは別の区別です。** セントラルとペリフェラルは「どちらが接続を申し込んだか」というリンク層の話で、クライアントとサーバは「どちらがデータを持っているか」という ATT の話です。

多くの場合「ペリフェラルがサーバ」になりますが、決まりではありません。たとえばスマートウォッチ（ペリフェラル）がスマホ（セントラル）の持つ時刻を読みに行くときは、スマホがサーバになります。1台の機器が同時に両方の役を担うこともあります。
:::

## 13.2 アトリビュート：表の1行

サーバの持つ表を**アトリビュートテーブル**といいます。表の1行が**アトリビュート**で、次の4つの要素からなります。

| 要素 | 意味 | 例 |
|---|---|---|
| **ハンドル** | この表の中での行番号 | `0x0012` |
| **UUID** | データの種類を表す番号 | `0x2A37`（心拍数の測定値） |
| **パーミッション** | 読み書きの許可と安全上の条件 | 読み取り可、暗号化が必要、など |
| **値** | データの本体（ただのバイト列） | `06 48` |

大事なポイントが2つあります。

**ハンドルと UUID の違い**　同じ種類の心拍データでも、機器によって表の何行目にあるかは違います。ですからクライアントは、まず UUID を手がかりに「この機器では心拍データは何行目か」を調べ、以後はハンドルで指定して読み書きします。

::: bio
UUID は遺伝子名、ハンドルはその個体のゲノム上の座標にあたります。同じ遺伝子でも、株が違えばゲノム上の位置が変わることがあります。「遺伝子名で検索して座標を調べ、以後は座標でアクセスする」のと同じ流れです。
:::

**値の意味は ATT では決めない**　ATT にとって値はただのバイト列です。`06 48` が「心拍数 72」を意味するかどうかは、第14章の上位の仕様が決めます。

::: se
ATT は、主キー（ハンドル）と型（UUID）と値を持つ小さな KVS を、ネットワーク越しに操作するプロトコルと考えられます。
:::

## 13.3 やり取りの4パターン

ATT には31種類の PDU がありますが、やり取りの型は6つの方式（コマンド、リクエスト、レスポンス、通知、インディケーション、確認）で、組み合わせると4パターンに整理できます。

| | 確認あり | 確認なし |
|---|---|---|
| **クライアント → サーバ** | リクエスト／レスポンス | コマンド |
| **サーバ → クライアント** | インディケーション／確認 | 通知（ノーティフィケーション） |

確認なしのパターンは、速くて軽いのが利点です。次の PDU を送るのに返事を待たなくて済みます。心拍数のように次々に新しい値が来るデータなら、1回くらい失われても困らないので通知が向いています。逆に、「設定を変更した」のように確実に伝えたい内容には確認ありのパターンを使います。

::: se
サーバ主導の通知は、ポーリングをせずにデータを受け取るしくみです。WebSocket のサーバプッシュに相当します。「確認なし」でも、第7章で見たとおりリンク層では再送されるので、電波が悪いとすぐ消えるわけではありません。
:::

エラーの場合は、サーバが `ATT_ERROR_RSP` を返します。

すべての PDU は、種類を示す**オペコード**、パラメータ、そして省略可能な署名、という同じ形をしています。

## 13.5 トランザクションの制約

リクエストとレスポンス、インディケーションと確認の組を、**トランザクション**と呼びます。ATT には次の厳しい決まりがあります。

- **同時に1つ**：進行中のトランザクションが終わるまで、次を始められない
- **30秒ルール**：30秒以内に完了しなければ失敗とする。失敗すると、そのチャネルではもう PDU を送れない

この「同時に1つ」は、複数のアプリが同じ機器を使うと問題になります。あるアプリの処理が遅いと、他のアプリも待たされるのです。

## 13.6 EATT：渋滞の解消

そこで Core 5.2 で **EATT**（Enhanced ATT）が登場しました。ATT を運ぶ L2CAP のチャネル（**ベアラ**と呼びます）を増やせるようにしたものです。

| | 従来の ATT ベアラ | 拡張 ATT ベアラ（EATT） |
|---|---|---|
| L2CAP のチャネル | 固定チャネル1本のみ | 動的チャネルを複数 |
| 並行処理 | できない | ベアラごとに1つずつ、並行して実行できる |
| MTU の決め方 | ATT の交換手順で決める | L2CAP の MTU をそのまま使う |
| フロー制御 | なし | クレジット方式 |
| 通知の信頼性 | バッファがあふれると失われる | 信頼できるとみなせる |
| 暗号化 | あってもなくてもよい | 必須 |

::: se
HTTP/1.1 のキープアライブ接続から、HTTP/2 の多重化ストリームへの進化を思い浮かべると近いかもしれません。1つの遅い処理が他を止めてしまう問題（head-of-line blocking）を解消します。
:::

EATT を使えるかどうかは相手次第です。GATT の中の決まった場所（Server Supported Features という項目）を読めば、相手が対応しているかどうかが分かります。

::: primer
- **§12.2**：PDU の形式と署名の話（暗号化された接続では署名は不要になるという説明）
- **§12.4**：ベアラごとの PDU の扱い（`ATT_MULTIPLE_HANDLE_VALUE_NTF` など、任意か必須かの違い）
- **§12.5**：EATT 対応を調べるビットの場所（Server Supported Features と Client Supported Features）
- **Understanding Security in Bluetooth LE**：パーミッションの詳しい説明がある SIG の学習ガイド
:::

## まとめ

- ATT はサーバの持つアトリビュートテーブルをクライアントが読み書きするプロトコルである
- アトリビュートはハンドル、UUID、パーミッション、値からなる
- クライアントとサーバは、セントラルとペリフェラルとは別の区別である
- やり取りは「向き」と「確認の有無」の組み合わせで4パターンある
- 従来の ATT は同時に1トランザクションだけ。EATT で並行処理とフロー制御ができるようになった

## 確認問題

1. 2台の同じ型の心拍計で、心拍データの UUID とハンドルはそれぞれ同じになるでしょうか。別のメーカーの心拍計ではどうでしょうか。
2. スマホからの「ライトを点灯する」という命令には、コマンドとリクエストのどちらが適切でしょうか。
3. サーバからクライアントへ、確実に届いたことを確かめて情報を送りたいとき、何を使いますか。
4. 従来の ATT で、あるアプリのリクエストに対してサーバが25秒かけて返事をしました。その間、同じ機器の別のアプリはどうなるでしょうか。

::: details 答え
1. UUID はどれも同じです（種類を表すため）。ハンドルは、同じ型なら同じことが多いですが、別のメーカーなら異なっていて当然です。
2. 状況によりますが、点灯したことを確かめたいならリクエスト（確認あり）です。連続して大量に送る操作ならコマンドも候補です。
3. インディケーションです。
4. トランザクションが1本しか走れないので、別のアプリのリクエストは待たされます。これが EATT で解消したい問題です。
:::
