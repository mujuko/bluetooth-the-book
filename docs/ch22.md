# 第22章 見つける、つなぐ

::: goal
- Inquiry と Page の違いを説明できる
- お互いの時計を知らない2台が出会えるしくみを説明できる
- Page の6つのステップを順に言える
- 「発見可能」と「接続可能」の違いを、製品の動作と結びつけて説明できる
:::

スマートフォンの設定画面を開くと、周りの機器が少しずつ一覧に現れます。これが **Inquiry** です。一覧の機器をタップしてつなぐのが **Page** です。Classic の接続は、この2段階でできています。

## 22.2 難問：時計も周波数も分からない

接続中のピコネットでは、全員が同じ時計と同じ跳び方を共有していました。でも、出会う前の2台は何も共有していません。79本もチャネルがあるのに、相手が今どの周波数を聞いているのか分からないのです。

解決の鍵は3つあります。

1. **聞く側はゆっくり、呼ぶ側は速く動く**
2. **呼ぶ周波数を絞る**（79本ではなく32本）
3. **呼ぶ側は、1回で複数の周波数に声をかける**

具体的な数字を Inquiry で追いましょう。

**聞く側（Inquiry Scan）** は、1つの周波数でじっと待ちます。既定では 2.56 秒ごとに 11.25 ms だけ聞き、聞く周波数は 1.28 秒ごとに変わります。聞いている時間の割合はわずかです。

<div class="formula">11.25 ms ÷ 2560 ms ≒ 0.44%</div>

**呼ぶ側（Inquiry）** は、ID パケットを次々と別の周波数で送ります。1スロットに2回送り、次のスロットで返事を2つ分聞きます。跳ぶ速さは通常の2倍の **1秒に3200回**です。こうすると、32本のうちの16本を 10 ms で一巡できます。この16本の組を**トレイン**と呼びます。

ここが巧妙なところです。

<div class="formula">聞く時間 11.25 ms ＞ トレイン1周 10 ms</div>

聞く側の窓は、トレインの一周より少し長く開いています。だから聞いている周波数がトレインに含まれていれば、電波の状態がよい限り、窓が開いている間に声が届きます。

32本を16本ずつ A と B の2つのトレインに分け、一方を 256 回繰り返したら（2.56 秒）、もう一方に切り替えます。聞く側の周波数が変わることも考えると、電波の状況がよくても発見できない機器がないようにするには何度か切り替えが必要で、Inquiry は**約 10.24 秒**続きます。設定画面で機器が少しずつ現れるのはこのためです。

::: tip LE と見比べると
LE では、見つけてほしい機器が短いアドバタイズをときどき出し、探す側がじっと聞いていました（[第6章](./ch06)）。Classic は**役割が逆**です。探す側が大声で叫び続け、見つけてほしい機器はたまに耳を澄ますだけです。

どちらも「電力に余裕のある側が頑張る」という発想ですが、探す側が頑張る中身が違います。LE は「ずっと聞く」、Classic は「ずっと叫ぶ」です。チャネルの数も違います。LE は3本に絞ることで「ずっと聞く」だけで済ませました。
:::

## 22.3 Inquiry の返事

聞く側が ID パケットを捕まえたら、625 µs 後に **FHS パケット**で返事をします。FHS には次の情報が入っています。

| 情報 | 使い道 |
|---|---|
| BD_ADDR | Page の宛先 |
| 時計の値 | Page のときに相手の周波数を予測する |
| Class of Device | 機器の種類（オーディオ、キーボードなど）。アイコンの表示に使う |
| Page Scan の設定 | Page のときの戦略を決める |

さらに、**EIR**（Extended Inquiry Response）という追加のパケットを、FHS の送信を始めてから 1250 µs 後に同じ周波数で送れます。機器の名前や対応サービスの UUID を、最大 240 バイトまで載せられます。形式は LE のアドバタイズのデータとそっくりです（[第15章](./ch15)）。EIR がなかった頃は、機器名を知るために、見つけた機器へ1台ずつ接続して名前を聞く必要がありました。

ランダムに待つのは、同じ呼びかけに複数の機器が一斉に返事をしてぶつかるのを避けるためです。

呼びかけの ID パケットに、探す側の情報は入っていません。探される側は、誰に探されたのか分からないまま答えます。呼びかけの合言葉（IAC）には、全機器向けの GIAC（LAP は `0x9E8B33`）のほかに、限定された用途の DIAC もあります。予約された `0x9E8B00`〜`0x9E8B3F` の LAP は、普通のアドレスには使えません。

## 22.4 Page：特定の相手を呼ぶ

アドレスが分かれば Page です。Page Scan 中の相手は、**自分のアドレスから作った合言葉と周波数の列**で聞いています。呼ぶ側も相手のアドレスからそれを計算できるので、ほかの機器に邪魔されません。

周波数の問題は Inquiry と同じですが、Page では有利なことがあります。Inquiry や前回の接続で、**相手の時計のおよその値**を知っていることです。これが分かれば、相手が今聞いている周波数を予測し、その周りの16本をトレイン A として先に呼べます。

Page は6つのステップからなります。

③の FHS で、Peripheral はピコネットの3点セット（時計、跳び方、合言葉）を計算するのに必要な情報をすべて受け取ります。そして④の後、両者は一斉に新しいピコネットのホッピングへ移ります。⑤と⑥は、本当に移れたかの確認です。

**呼んだ側が Central になる**ことを覚えておいてください。ヘッドホンのほうからスマホへ Page すれば、ヘッドホンが Central です。これが不都合なときの話は[第26章](./ch26)の役割の交代で扱います。

相手の時計が分からない場合はどうでしょう。Page Scan の既定の間隔は 1.28 秒なので、トレイン A を 128 回（1.28 秒）繰り返し、だめならトレイン B に切り替えます。電波の状況がよければ、最悪でも 2.56 秒ほどで届く計算です。

### HCI から見ると

アプリに近いホストからは、一連の流れは少数のコマンドに見えます。HCI の基本は[第11章](./ch11)を見てください。

| 操作 | HCI のコマンドとイベント |
|---|---|
| 探す | `HCI_Inquiry` → `HCI_Extended_Inquiry_Result` など → `HCI_Inquiry_Complete` |
| つなぐ側 | `HCI_Create_Connection` → `HCI_Connection_Complete` |
| 受ける側 | `HCI_Connection_Request` → `HCI_Accept_Connection_Request` → `HCI_Connection_Complete` |

ホストが呼ぶのはコマンド1つだけで、トレインや FHS はコントローラが自動で処理します。

## 22.5 発見可能と接続可能

GAP は、機器の振る舞いを2つの独立したスイッチで定めています（[第15章](./ch15)の LE の GAP と同じ考え方です）。実際に HCI の `HCI_Write_Scan_Enable` というコマンドで、Inquiry Scan と Page Scan をそれぞれオンとオフにできます。

| Inquiry Scan | Page Scan | 状態 | 製品の例 |
|---|---|---|---|
| オフ | オフ | 見えない、つながらない | 省電力で待っているとき |
| オフ | **オン** | 知っている機器からだけつながる | ペアリング済みのヘッドホンの普段の状態 |
| **オン** | **オン** | 新しい機器からも見える | ヘッドホンのペアリングモード |
| オン | オフ | 見えるが、つなげない | 用途は限られる |

**普段は発見可能にしない**ことには、2つの利点があります。周囲に自分の存在を知らせずに済み、電力も節約できます。ヘッドホンのボタンを長押しして「ペアリングモード」にするのは、Inquiry Scan をオンにする操作です。

発見可能のモードには次の種類があります。

| モード | 意味 |
|---|---|
| 非発見 | Inquiry に応答しない |
| 限定発見 | 短い時間だけ発見可能。推奨は最大 1 分 |
| 一般発見 | 期間を定めず発見可能 |

発見可能にするなら、最低 30.72 秒はその状態を続けることになっています。あまり短いと、探している機器に見つけてもらえないおそれがあるからでしょう。

::: bio
Inquiry は、走化性のシグナルに似ています。放出側は誰が受け取るかを知らず、受け手はたまたま受容体が開いているタイミングで検知します。一方、Page は特定の受容体にだけ結合するリガンドのように、宛先の分子（DAC）で相手を選びます。
:::

## まとめ

- Classic の接続は、周りを探す Inquiry と、特定の相手を呼ぶ Page の2段階である
- 聞く側は同じ周波数で短くじっと待ち、呼ぶ側は 3200 回/秒の速さで周波数を変えながら叫ぶ
- 窓 11.25 ms がトレイン 10 ms より長いので、周波数が合えば捕まえられる
- FHS がアドレスと時計を伝える。Page の③の FHS で Peripheral はピコネットに入る情報を得る
- 呼んだ側が Central になる
- ペアリング済みの機器は普段、Page Scan だけをオンにしている

## 確認問題

1. Inquiry を行うと手に入る情報のうち、Page を高速にするものは何でしょうか。
2. ヘッドホンをペアリングモードにしていなくても、前につないだスマホから接続できるのはなぜでしょうか。
3. Inquiry Scan の窓の長さが 5 ms だと、どんな問題が起きるでしょうか。
4. Page のステップ⑤の POLL を、なぜ Central が送るのでしょうか。

::: details 答え
1. 相手の時計の値（および Page Scan の設定）です。これで相手が聞く周波数を予測できます。
2. ペアリングモードでオンになるのは Inquiry Scan だけで、Page Scan は普段からオンになっているからです。スマホはアドレスを覚えているので、Inquiry なしで Page できます。
3. トレインの一周（10 ms）より短いので、聞いている周波数がトレインに含まれていても、窓の間に呼びかけが来ない場合があります。
4. ピコネットでは Central が話すきっかけを作り、Peripheral は呼ばれてから話すからです。POLL は返事を要求するので、両者が新しいホッピングに移れたことを確かめられます。
:::
