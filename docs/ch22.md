# 第22章 コネクション：約束して話す

::: goal
- 接続イベントとコネクション間隔のしくみを図で説明できる
- Peripheral レイテンシとスーパービジョンタイムアウトの役割を説明できる
- SN と NESN という2つのビットで再送が成り立つ理由を説明できる
- 適応型周波数ホッピングがなぜ混信に強いのかを説明できる
:::

アドバタイズは一方的でした。この章では、2台が約束を交わして確実にデータをやり取りする **LE-ACL** を学びます。LE でいちばんよく使われる通信の型で、単に「コネクション」といえばこれを指します。

## 22.1 接続は「約束」である

スマホが心拍計の `ADV_IND` を受け取り、接続したいとします。スマホは受信の直後に、同じチャネルで `CONNECT_IND` を送ります。この短いパケットの中に、これからの通信の約束がすべて書かれています。

| 約束の内容 | 意味 |
|---|---|
| アクセスアドレス | この接続専用の札（第20章） |
| コネクション間隔 | 何ミリ秒おきに通信するか |
| Peripheral レイテンシ | Peripheral が何回サボってよいか |
| スーパービジョンタイムアウト | 何秒黙っていたら切れたとみなすか |
| チャネルマップ | どのチャネルを使うか |

受け取った瞬間から、スマホは Central、心拍計は Peripheral になります。

ここで大切なのは、接続といっても、**電線のようにつながり続けているわけではない**ことです。2台は「次はいつ起きるか」という予定を共有しているだけで、ほとんどの時間はお互いに無線を止めています。

Classic の Active な接続では、Peripheral は呼ばれるかもしれないスロットを毎回聞いていました（[第6章](./ch06)）。LE の接続は、こうした常時の待ち受けをしません。

::: analogy 定期的な電話の約束
遠距離の友達と「毎晩9時に電話しよう」と決めるのに似ています。電話をつなぎっぱなしにはしません。9時になったら話し、用が済んだらすぐ切って、次の9時まで別のことをしています。かけるのはいつも Central 側です。
:::

## 22.2 接続イベント

コネクション間隔ごとに訪れる通信の機会を**接続イベント**といいます。イベントが来ると、次のように進みます。

1. Central が先に送信する
2. Peripheral は、受信の 150 µs 後に返事を送る（Core 6.0 からは、この間隔を接続ごとに変えられる）
3. まだ送るデータがあれば、交互に続ける
4. 用が済んだら、次のイベントまで眠る

イベントには16ビットの通し番号がついています。2台は同じ番号を数えていて、これが 22.5 節のホッピングにも使われます。

往復を続けるかどうかは、パケットの **More Data** という1ビットで伝えます。「まだあるよ」のビットが両者とも立っていなければ、イベントは終わりです。

コネクション間隔は、機器の性格に合わせて選びます。短ければ反応が速く通信量も増やせますが、電池を消耗します。第18章と同じ計算を、1イベント 3 ミリ秒、7 mA として試してみましょう。

| コネクション間隔 | 動作の割合 | 平均電流 | CR2032 での寿命（約） |
|---|---|---|---|
| 30 ms | 10% | 0.70 mA | 13 日 |
| 100 ms | 3% | 0.21 mA | 44 日 |
| 1 秒 | 0.3% | 0.023 mA | 1年あまり |

::: extra 間隔の範囲
長らく、コネクション間隔の範囲は 7.5 ミリ秒から 4 秒でした。Core 6.2 からは、対応する機器どうしなら 7.5 ミリ秒より短い間隔も選べます（仕様上の下限は 375 µs）。
:::

## 22.3 Peripheral レイテンシ：サボる権利

心拍計のように「ふだんは送るものがなく、変化があるときだけ送りたい」機器を考えましょう。反応を速くしたいなら間隔を短くしたい。しかし、毎回起きていては電池がもちません。

そこで**Peripheral レイテンシ**です。これは「Peripheral は、この回数までのイベントを無視してよい」という権利です。

<figure class="fig">
<Timing :max="100" :rows="[{name:'Central',blocks:[{x:5,w:7,c:'b'},{x:30,w:7,c:'b'},{x:55,w:7,c:'b'},{x:80,w:7,c:'b'}]},{name:'Peripheral',blocks:[{x:12.5,w:7,c:'a'},{x:37.5,w:7,ghost:true},{x:62.5,w:7,c:'a'},{x:87.5,w:7,ghost:true}]}]" :spans="[{x1:5,x2:30,row:1,t:'間隔'}]" :marks="[{x:5},{x:30},{x:55},{x:80}]" />
<figcaption>図22-2 Peripheral レイテンシが1の場合。点線のイベントでは Peripheral は眠っている</figcaption>
</figure>

うまいのは、**送りたいデータがあるときは、Peripheral はいつでも次のイベントで起きて話せる**ことです。たとえば間隔 30 ms、レイテンシ 9 にすれば、ふだんは 300 ms に1回しか起きないのに、送りたいデータがあれば 30 ms 以内に送れます。

その代わり、Central から Peripheral への通信は、起きてくれるまで待たされます（この例では最大 300 ms）。方向によって反応の速さが違う、という点に注意してください。

もうひとつの約束が**スーパービジョンタイムアウト**です。これは「この時間、相手からパケットを受信できなければ、接続が切れたとみなす」という期限です。相手が圏外へ出たり電池が切れたりしたときに、いつまでも待ち続けずに済みます。

## 22.4 確実に届ける：SN と NESN

電波は失敗するものです。LE-ACL は、再送のしくみでこれを乗り越えます。驚くことに、使うのはたった2つのビットです。

- **SN**（Sequence Number）：このパケットの番号。0 か 1
- **NESN**（Next Expected Sequence Number）：次に受け取りたい番号。0 か 1

規則は3つです。

1. 相手から期待どおりの SN が来たら、新しいデータとして受け取り、NESN を反転させる
2. 期待と違う SN が来たら、同じものの再送なので、データは捨てて確認だけ返す
3. 相手の NESN が自分の SN と違っていれば「届いた」ということなので、次のデータに進む（SN を反転）。同じなら届いていないので、同じ SN のまま再送する

なぜ 1 ビットで足りるのでしょうか。同時に「未確認」のパケットを1つしか持たないからです。今のパケットと次のパケットを区別できれば十分なので、番号は 0 と 1 の2つで足ります。

Classic の ARQN と SEQN（[第10章](./ch10)）も、同じように番号を1ビットだけ使う考え方でした。

CRC が合わなかったときも同じです。受信側はそのパケットを受け取らなかったものとして扱い、確認を進めません。すると送信側は「届いていない」と判断して再送します。第20章で「CRC は検出するだけ」と言いましたが、このしくみと組み合わせることで、誤りが訂正されるのと同じ結果が得られるわけです。

::: se
TCP を極限まで簡単にしたような「ストップ・アンド・ウェイト ARQ」です。ただし、この信頼性はあくまで無線の1区間（相手のリンク層まで）についてのものです。相手のアプリに届いたことまでは保証しません（第26章）。
:::

## 22.5 適応型周波数ホッピング

2.4 GHz 帯は混雑しています。Wi-Fi が動いているチャネルでは、Bluetooth のパケットは失敗しやすくなります。そこで LE-ACL は、接続イベントごとに使うチャネルを変えていきます。これが**周波数ホッピング**です。

2台は通信しなくても次のチャネルが分かります。チャネルを決める計算式（チャネル選択アルゴリズム）と、その入力（イベントの通し番号など）を共有しているからです。外から見るとランダムに飛んでいるようですが、当事者にとっては決定的に定まります。

さらに賢いのが「適応型」の部分です。Central は**チャネルマップ**という表を持っていて、37本それぞれに「使う」「使わない」の印をつけています。調子の悪いチャネルを「使わない」にすれば、ホッピングの飛び先から外れます。

チャネルマップが更新されたら、Peripheral にも知らせます。Peripheral も自分の周囲の状況を測って「このチャネルは悪い」と Central に報告できます（チャネル分類の報告）。Peripheral の周りの混信は、Central の場所からは分からないことがあるからです。

こうして LE は、Wi-Fi のように決まったチャネルに居座る無線と共存できます。

Classic の AFH（[第16章](./ch16)）と同じ考え方です。ただし、Classic は最低20本のチャネルを使わなければならないのに対し、LE は2本まで減らせます。

## 22.6 接続中の制御

接続が始まったあとも、リンク層どうしで制御用のやり取りができます。代表的なものを挙げます。

| 手続き | 内容 |
|---|---|
| コネクション更新 | 間隔、レイテンシ、タイムアウトを変更する |
| チャネルマップ更新 | 新しいチャネルマップを伝える |
| 暗号化の開始 | パケットの暗号化を始める（第30章） |
| 機能の交換 | お互いに対応している機能を教え合う |
| 送信電力制御 | 相手に送信の強さの調整を頼む |
| CIS の作成 | アイソクロナスのストリームを作る（第24章） |

::: deep 時計のずれという現実
2台の予定がぴったり合うためには時計が正確でなければなりませんが、小さな機器の水晶発振器にはわずかな誤差があります。次のイベントまでの時間が長いほどずれも大きくなるので、Peripheral はずれの分だけ早めに起きて受信を始めます。間隔を長くすると節電になる一方で、この余分な待ち時間は長くなります。「間隔を長くすればするほど得」というわけではないのです。この早起きの分は、コア仕様ではウィンドウ・ワイドニングと呼ばれ、計算式も決められています（原本には出てこない話です）。
:::

## 22.7 サブレーティング：寝ながら即応する

コネクション更新で間隔を変えるのは、実は時間がかかります（変更の予告が必要だからです）。ところが補聴器のように、ふだんは静かにしておき、電話がかかってきたら瞬時に音声を流したい機器もあります。

Core 5.3 の**サブレーティング**はこれに応えます。短い間隔の接続イベントを設定しておき、そのうち数回に1回だけ実際に使うのです。

## まとめ

- 接続は電線ではなく「次に起きる時刻の約束」である。`CONNECT_IND` に約束のすべてが書かれている
- コネクション間隔ごとの接続イベントで、Central から先に交互に話す
- Peripheral レイテンシはサボる権利。送りたいときはいつでも送れる
- SN と NESN の2ビットで、確認応答、再送、重複の排除ができる
- 周波数ホッピングで混信に強くなり、チャネルマップで悪いチャネルを避ける

## 確認問題

1. コネクション間隔 50 ms、Peripheral レイテンシ 3 のとき、Peripheral はデータがなければ何ミリ秒おきに起きますか。
2. 図22-3 の「返事のほうが失われた場合」で、もし SN の判定がなかったら何が起きるでしょうか。
3. 接続中の2台が、通信しなくても次のチャネルに同時に移動できるのはなぜでしょうか。

::: details 答え
1. 3回サボって4回目に起きるので、50 × 4 = 200 ms おきです。
2. 同じデータが Peripheral の上の層に2回渡ってしまいます（心拍数なら害は小さいですが、「1回押された」という操作なら大問題です）。
3. チャネル選択アルゴリズムと、その入力（イベントの通し番号など）、チャネルマップを共有しているので、同じ答えを別々に計算できるからです。
:::
