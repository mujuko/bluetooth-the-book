# 第30章 混雑をよける

::: goal
- 適応ホッピング（AFH）のしくみを説明できる
- 同じ製品の中の Wi-Fi やモバイル通信と Bluetooth がぶつかる理由を説明できる
- 共存の4つの方向性（周波数、時間、タイミング合わせ、混合）を区別できる
:::

2.4 GHz 帯は混雑しています。Wi-Fi、電子レンジ、コードレス電話、ほかの Bluetooth 機器。スマートフォンの中では、Bluetooth のアンテナと Wi-Fi のアンテナが数センチの距離に並んでいます。この章では、混雑の中で Classic がどう生き延びているかを見ます。

## 30.1 適応ホッピング（AFH）

[第20章](./ch20)で見たように、79本のチャネルを跳び回っていれば、誰かとぶつかっても一瞬で済みます。ただ、Wi-Fi のように**広い帯域に居座る相手**がいると、その範囲に跳ぶたびに失敗してしまいます。

そこで、Core 1.2 で **AFH**（Adaptive Frequency Hopping）が導入されました。考え方は単純です。

これが第23章で出てきた**適応ピコネットチャネル**です。基本ピコネットチャネルと時計も合言葉も同じで、周波数の選び方だけが違います。ここには重要な点が2つあります。

**1つ目**は最低の本数です。Classic は **20本以上**を使わなければなりません。LE は 2 本まで減らせます（ARCH §7.2）。

**2つ目**は、Peripheral が「Central が直前に話した周波数で返事をする」ことです。基本チャネルでは1スロットごとに跳びましたが、適応チャネルでは Central のスロットの周波数を Peripheral の応答でも使います。これを**同一チャネルのしくみ**（same channel mechanism）と呼びます。Central の送信が届いたチャネルは、少なくともその瞬間は干渉が少ないので、返事も通りやすいはずです。

### マップはどう決めるのか

チャネルは Central と Peripheral がそれぞれの判断で次の3つに分類します。

| 分類 | 意味 |
|---|---|
| good | 問題なく使える |
| bad | 失敗や干渉が多い |
| unknown | 判断の材料が足りない |

材料はいくつかあります。

- 自分で測定した結果（受信できなかったパケットの統計、電波の強さなど）
- ホストからの情報（`HCI_Set_AFH_Host_Channel_Classification`）。たとえば「いま Wi-Fi はこのチャネルを使っている」という OS の情報
- Peripheral からの報告（Central が求めた場合）

最終的に **Central が決めて**、`LMP_SET_AFH` で Peripheral に伝えます。切り替えるスロットの番号も一緒に伝えるので、全員が同時に新しいマップへ移れます。

Peripheral ごとに別のマップを使うこともできます。場所によって干渉の様子が違うからです。AFH に対応していない古い Peripheral には、基本チャネルで話します。Central は時間を分けて両方の物理チャネルを使い分けます。

::: extra コア仕様の外からの補足：Wi-Fi 3本は避けきれない
2.4 GHz の Wi-Fi は1チャネルが約 20 MHz を占めます。互いに重ならない 1、6、11 番を全部避けようとすると、次のようになります。

<div class="formula">79 − 20 × 3 ＝ 19 本 ＜ 最低の 20 本</div>

1本足りません。実際には、集合住宅のように3チャネルとも混雑している場所では、AFH で完全に避けることはできず、再送で補うことになります。Bluetooth が混雑した場所で途切れやすいのは、こういう事情もあります。
:::

## 30.2 共存の4つの方向性

Bluetooth の機器は、離れた場所の電波を避けるだけでは足りません。一番の問題は、**同じ製品の中の別の無線**です（collocated、同居）。スマートフォンの Bluetooth と Wi-Fi のアンテナは数センチしか離れていないので、片方が送信すると、もう片方は受信できなくなることがあります。

Architecture 編は、対策を次の4つに分類しています。

| 方向性 | 考え方 | 例 |
|---|---|---|
| **周波数で分ける** | フィルタや距離で分離し、同時に使う | 帯域通過フィルタ、AFH |
| **時間で分ける** | 同時には1つの無線しか動かさない | Wi-Fi との優先制御 |
| **タイミングを合わせる** | 「送信どうし」「受信どうし」を同時にする | LTE に Bluetooth のスロットを合わせる |
| **混合** | 周波数に応じて上の3つを使い分ける | 隣接する周波数のとき |

3つ目は少し面白い考え方です。2つの無線が同時に**送信**するなら、どちらも受信していないので問題ありません。**送信と受信がぶつかるとき**だけが問題です。だから、お互いのタイムテーブルを合わせれば、衝突を減らせます。

## 30.3 Wi-Fi との共存

同じチップやアンテナを共有する Wi-Fi との協調は、AFH に加えて、各社独自の方法で行われます。Core 仕様は、Bluetooth のコントローラと Wi-Fi の間の信号を定めていません（ARCH §7.3）。一般には、チップの中で「今はどちらが電波を使うか」を調停するしくみが動いています。

Wi-Fi で大きなファイルをダウンロードしている最中に音楽が途切れやすいことがあるのは、こうして時間を分け合っていることも一因です。

## 30.4 モバイル通信との共存

携帯電話の LTE などは 2.4 GHz の**隣の周波数**を使うことがあります。周波数が近いと、フィルタで分離しきれない場合があります。ここで出てくるのが **MWS**（Mobile Wireless Standards）との共存です。

Wi-Fi と違って、Core 仕様は標準の信号（Vol 7）を定めています。

LTE の TDD では、基地局が定めた枠で「送信」と「受信」の時間が決まっていて、Bluetooth はこれに合わせるしかありません。そこで Bluetooth 側を合わせるためのしくみが用意されています。

| 機能 | 導入 | 働き |
|---|---|---|
| Piconet Clock Adjustment | 4.1 | ピコネットの時計を外部の枠に合わせる |
| Train Nudging | 4.1 | Page と Inquiry の返事を受信できないスロットが周期的にあるとき、トレインをずらして成功率を上げる |
| Generalized Interlaced Scan | 4.1 | スキャンに使えないスロットが周期的にあるとき、窓の位置をずらして成功率を上げる |
| Slot Availability Mask（SAM） | 5.0 | 2台のあいだで「このスロットは空いている」という地図を交換する |

時計の調整には次の2つがあります。

| 方法 | 動き | 使いどころ |
|---|---|---|
| Coarse Clock Adjustment | LMP で通知して、一気に動かす | 大きなずれのとき。全 Peripheral の対応が必要 |
| Clock Dragging | スロットを数 µs 長く（短く）して、ゆっくり動かす | 微調整、または古い Peripheral がいるとき |

Clock Dragging は古い機器が付いてこられるように、ゆっくりとしか動かせません。1回のずらしは 3 µs 以下、125 ms のあいだに同じ向きへ合計 5 µs 以下と決まっています。1秒に直すと 40 µs ほどで、時計の誤差（±20 ppm、[第20章](./ch20)）と同じくらいの速さです。

同居の無線を持つ機器を Central にしておくと、時計の調整が楽です。Peripheral は自分で時計を決められないので、Central に頼む必要があります。ここにも[第26章](./ch26)の役割の交代が関わってきます。

::: bio
時間で分けて共存するしくみは、同じ環境で活動時間をずらす生態的な棲み分けに似ています。昼行性と夜行性に分かれて同じ資源を使う動物のように、2つの無線も「同時に使わない」ことで共存しています。周波数を分けるのは、同じ森で別の餌を食べるようなものです。
:::

## まとめ

- AFH は混雑したチャネルを跳び先から外すしくみで、最低 20 本を使う
- 適応チャネルでは、Peripheral は Central の直前の周波数で返事をする
- 分類は各機器が行い、最終的に Central が決める
- 同じ製品内の無線との共存は、周波数、時間、タイミング合わせ、混合の4方向で考える
- Wi-Fi との協調は各社の実装で、MWS との協調は Core 仕様が標準の信号を定めている
- 時計の調整、Train Nudging、Interlaced Scan、SAM は外部の枠に合わせるためのしくみである

## 確認問題

1. AFH で 79 本のうち 40 本を「使わない」としたとき、1スロットで使えないチャネルが疑似乱数で選ばれたらどうなるでしょうか。
2. Peripheral の返事が Central の直前の周波数を使うと、どんな利点があるでしょうか。
3. Bluetooth と LTE が同時に送信しても問題が少ないのはなぜでしょうか。
4. Coarse Clock Adjustment と Clock Dragging の使い分けはどう考えればよいでしょうか。

::: details 答え
1. 使えるチャネルの中から疑似乱数で選んだ別のチャネルに置き換えられます。
2. Central の送信が届いたばかりのチャネルは、その瞬間に干渉が少ないと考えられるので、返事も通りやすいはずです。
3. どちらも受信していないからです。問題になるのは、一方の送信ともう一方の受信が重なるときです。
4. 大きなずれには Coarse を使いますが、すべての Peripheral の対応が必要です。微調整や、対応していない機器がいるときには Dragging を使います。
:::
