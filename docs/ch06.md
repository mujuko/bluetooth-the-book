# 第6章 アドバタイズ：一方的に叫ぶ

::: goal
- 従来型アドバタイズのチャネルの使い方とタイミングを説明できる
- パッシブスキャンとアクティブスキャンの違いを説明できる
- 拡張アドバタイズが従来型の何を解決したのかを説明できる
- スキャン側の負担を減らす工夫を2つ挙げられる
:::

**アドバタイズ**は、機器が周囲に向かって一方的にパケットを出す、接続なしの通信です。論理トランスポートの名前でいえば ADVB（LE Advertising Broadcast）です。広告を意味する言葉ですが、その役割は2つあります。

- **存在を知らせる**：「ここに接続できる機器がいます」
- **データを配る**：接続しなくても、聞こえた全員にデータを届ける（ビーコンなど）

受信側を**スキャナ**と呼びます。スキャナは何台いてもかまいません。受信確認は返らないので、届いたかどうかは送る側には分かりません。この性質から、アドバタイズは「信頼性のない通信」と呼ばれます。その代わり同じ内容を繰り返し送ることで、いつかは届くようにします。

## 6.1 従来型アドバタイズの動き

Bluetooth 4 から使われている方式で、**レガシーアドバタイズ**と呼ばれます。

アドバタイズのたびに、同じパケットを3本の専用チャネル（37, 38, 39番）に順番に送ります。この一連の送信を**アドバタイズイベント**といいます。データの本体は最大31バイトです。

イベントの間隔（**アドバタイズ間隔**）は、およそ 20 ミリ秒から 10.24 秒の範囲で設定します。短ければすぐ見つけてもらえますが電池を消耗し、長ければ節約できますが見つかるのが遅くなります。

ここに巧妙な工夫がひとつあります。イベントの間隔に、毎回 0〜10 ミリ秒のランダムな遅れ（**advDelay**）を足すのです。もし2台の機器がぴったり同じ周期で送信していたら、一度タイミングが重なると永遠にぶつかり続けます。わざとばらつかせることで、ぶつかり続ける事態を防いでいるのです。

::: deep スキャナとアドバタイザのすれ違い
スキャナは一定の時間（スキャン窓）だけ1本のチャネルを聞き、チャネルを切り替えて、また聞きます。アドバタイザがいつ送るかは分かりません。お互いのタイミングが合ったときに初めて受信できるので、発見にかかる時間は確率的に決まります。

実はここにも非対称があります。聞く側はずっと無線を動かす必要があるので電力を多く使いますが、送る側は一瞬で済みます。スキャンの役をスマホに任せることで、小さな機器は楽ができます。
:::

## 6.2 アドバタイズの種類

リンク層は、目的に応じたアドバタイズの PDU を定義しています。「接続を受け付けるか」と「追加の問い合わせを受け付けるか」が区別のポイントです。

| PDU | 宛先 | スキャン要求を受ける | 接続を受ける | 用途の例 |
|---|---|---|---|---|
| `ADV_IND` | 全員 | ○ | ○ | 接続できる機器の一般的な呼びかけ |
| `ADV_DIRECT_IND` | 特定の相手 | × | ○ | 知っている相手に素早く再接続 |
| `ADV_SCAN_IND` | 全員 | ○ | × | データは配るが接続はしない |
| `ADV_NONCONN_IND` | 全員 | × | × | ビーコン |

スキャンする側が使う PDU もあります。

| PDU | 意味 |
|---|---|
| `SCAN_REQ` | もっと情報をください |
| `SCAN_RSP` | （アドバタイザの返事）追加の情報です |
| `CONNECT_IND` | 接続してください（第7章） |

## 6.3 パッシブスキャンとアクティブスキャン

スキャナには2つの聞き方があります。

- **パッシブスキャン**：聞くだけ。電波を出さない
- **アクティブスキャン**：スキャン要求を送って、追加の情報をもらう

31バイトは意外とすぐに埋まります。機器の名前を入れる余裕がないときなどは、名前をスキャン応答の31バイトに入れておきます。

## 6.4 拡張アドバタイズ：Bluetooth 5 の大改造

レガシーアドバタイズには弱点がありました。

- データが31バイトしか送れない
- 同じ内容を3回送るので、3本しかないチャネルが混雑する。機器が多い場所ではぶつかりやすい
- 同じ機器が目的の違う複数のアドバタイズを行う標準的な方法がない

Bluetooth 5.0 で導入された**拡張アドバタイズ**は、これらを一気に解決しました。発想は「**見出しと本文を分ける**」です。

3本の専用チャネル（ここでは**プライマリチャネル**と呼びます）には、短い見出しのパケット `ADV_EXT_IND` だけを送ります。その中に **AuxPtr** という欄があり、「本文は○番チャネルで、○ミリ秒後に送ります」と書いてあります。スキャナはそれを見てそのチャネルへ移動し、本文の `AUX_ADV_IND` を受け取ります。本文には残り37本の汎用チャネル（**セカンダリチャネル**）を使います。

::: analogy 駅の案内板
駅の案内板に、すべての案内の全文を書くわけにはいきません。「◯◯線の詳細は12番窓口へ」と短く書いておき、興味のある人だけが窓口に行きます。案内板の前の混雑は減り、窓口ではゆったり詳しい話ができます。
:::

本文を分けたことで、次のような利点が生まれました。

**データ量が増えた**　1パケットで最大254バイトのデータを運べます。さらにパケットを鎖のようにつないで（**チェイン**）、全体で最大1650バイトまで送れます。

**混雑が減った**　本文は1回しか送らないので、同じ量のデータを送るときの総送信量が少なくなります。専用チャネルは短い見出しだけで済むので、ぶつかる確率も下がります。

**PHY が選べる**　本文は 2M や Coded でも送れます。見出しも Coded で送れるので、遠くまで届くアドバタイズができるようになりました。

**アドバタイズセット**　1台の機器が、内容と設定の異なる複数のアドバタイズを同時に進められます。各セットには ID がつきます。「スマホには接続用の呼びかけを100ミリ秒ごとに、位置情報のビーコンは1秒ごとに」といった動作を、ホストを起こさずにコントローラが自動で進めてくれます。

| | レガシー | 拡張 |
|---|---|---|
| 最大データ量 | 31 バイト | 1650 バイト |
| 1パケットの最大データ量 | 31 バイト | 254 バイト |
| 使うチャネル | 37, 38, 39 | すべて（見出しは 37〜39、本文は 0〜36） |
| PHY | LE 1M のみ | LE 1M, 2M, Coded（見出しは 1M か Coded） |
| 同時に使える設定の数 | 1 | 16 |
| タイミング | 非同期のみ | 定期的なものも可（第8章） |

## 6.5 スキャン側の苦労を減らす

ここまでは送る側の話でした。受ける側にも問題があります。

### 同じパケットが何度も来る

機器が20ミリ秒ごとにアドバタイズしていれば、スキャナは同じ内容を毎秒何十回も受信します。そのたびにコントローラからホストへ報告し、さらにアプリを呼び出すのは無駄です。そこでホストは「重複は報告しないで」と頼めます（重複フィルタ）。

しかし、これには副作用があります。報告が来なくなったとき、「重複だから来ないのか、相手が遠ざかったのか」が区別できません。ユーザーが画面で機器を選んだのに、もう圏外だった、という無駄が起こります。電力を使って激しくスキャンしたあげく、相手がいなかったことになります。

Core 6.0 の **Monitoring Advertisers（アドバタイザの監視）** はこれを解決します。ホストは監視したい機器と、信号の強さのしきい値（上限と下限）、そしてタイムアウトをコントローラに登録します。コントローラは、信号が下限を下回ったまま時間切れになれば「見失った」、再び上限を超えれば「戻ってきた」とだけ報告します。重複はふるい落としたまま、存在だけを把握できるわけです。

### 興味のない本文を聞きに行ってしまう

拡張アドバタイズのスキャナは、AuxPtr があれば必ず本文を受信しに行きます。ところが、中身を見て初めて「関係なかった」と分かることがあります。しかも本文を受信している間は、プライマリチャネルを聞けないので、他の機器を聞き逃すかもしれません。この無駄足は**ディストラクション**と呼ばれます。

Core 6.0 の **Decision-Based Advertising Filtering（DBAF、判断ベースのフィルタ）** は、見出しに判断材料を載せられるようにしました。アドバタイザは `ADV_DECISION_IND` という PDU を使い、そこに短い判断用データを入れます。スキャナのコントローラは、ホストからあらかじめ教わった条件で判定し、合うものだけ本文を聞きに行きます。

::: se
重複フィルタとアドバタイザの監視は、ポーリングをやめて状態変化イベントだけを受け取る設計に似ています。DBAF は、本文を取得する前にヘッダだけで判定する HTTP の `HEAD` リクエストのようなものです。
:::

## まとめ

- アドバタイズは一方的な放送で、機器の発見とデータ配布に使う。受信確認はない
- レガシーでは3本のチャネルに同じ内容を送る。間隔にランダムな遅れを足して、衝突が続くのを防ぐ
- スキャナは聞くだけ（パッシブ）か、追加を問い合わせる（アクティブ）かを選べる
- 拡張アドバタイズは見出しと本文を分け、大きなデータ、複数の設定、複数の PHY を可能にした
- Core 6.0 でスキャン側の負担を減らす機能が加わった

## 確認問題

1. アドバタイズ間隔にランダムな遅れを足すのは何のためでしょうか。
2. 電波の様子を観測すると、37, 38, 39番のチャネルに短いパケットが出たあと、別のチャネルに長いパケットが出ていました。これはレガシーと拡張のどちらでしょうか。
3. 全員に配る気温データを、接続せずに1分ごとに流すセンサを作ります。レガシーの PDU ならどれが適切でしょうか。

::: details 答え
1. 同じ周期の機器どうしでパケットの衝突が続くのを防ぐためです。
2. 拡張アドバタイズです。短いパケットが見出し（`ADV_EXT_IND`）、長いパケットが本文（`AUX_ADV_IND`）です。
3. `ADV_NONCONN_IND` です。接続もスキャン要求も受け付けないので、そのぶん受信の時間が不要になり、節電にもなります。
:::
